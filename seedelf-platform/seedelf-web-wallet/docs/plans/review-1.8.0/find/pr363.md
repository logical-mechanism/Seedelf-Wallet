### pr363#0

- **Severity:** low. **Kind:** code (words). **Introduced:** reachable.
- **Title:** A v2 start is told it makes a copy of an 8131b1d start of the same values that 1.7.2 recorded.
- **Where:** `seedelf-platform/seedelf-web-wallet/extension/src/background/lovejoin-launch.ts:298-305` (`startedBefore`), `extension/src/background/lovejoin.ts:1007-1020` (`LaunchRecord`, no set), `extension/src/background/lovejoin-launch.ts:394-402` (`recordLaunch`), `extension/src/i18n/translations/en.json:1387` (`lovejoin.launch.warn.startedBefore`, a critical key).
- **Claim:** 44a split the shown rule by set: a v2 pool is never a copy of an 8131b1d pool, and the launch's own copy check (`build`, line 247) now matches v2 pools alone. `startedBefore` still matches the wallet's recorded starts by values alone, and a `LaunchRecord` doesn't say which set its start ran. So a start recorded by 1.7.2 (8131b1d's scripts, as every 1.7.2 start was) makes a v2 start of the same values get the critical warning "If both starts go through, the later one is a copy: never shown, and what it locks is gone for good." That's false: the v2 pool is the first of its values on its set, so it's shown.
- **Scenario:** On 1.7.2 the user starts a pool of 4.5 ₳ and 1000 MIN a box. It's recorded (`{ id, txHash, from, box }`). Within the next day, and before a look finds it (minutes, or the whole day if that start lost a race or never landed), the wallet updates to 1.8.0. The user starts the same values again, now on v2 (the old pool is retired). The review shows `lovejoin.launch.warn.startedBefore`. Nothing is refused, but the review tells the user the new pool will be a copy that's never shown. That could put them off a launch that's fine.
- **Evidence:** I added a scratch test to `extension/tests/lovejoin-flows.test.ts` beside the existing 318-worker#1 test (saved as `pr363-mut/lovejoin-flows.pr363-started-before.test.ts`). It records an 8131b1d start of `{ lovelace: "4500000", token: MIN × 1000 }` the way `recordLaunch` does, moves the clock 5 minutes, and builds the same values. `npx vitest run tests/lovejoin-flows.test.ts --maxWorkers=2 -t "pr363"` gives `× pr363: a v2 start isn't told it makes a copy of an 8131b1d start that 1.7.2 recorded`, `AssertionError: expected { …(2) } to be undefined` at `expect(v2.startedBefore).toBeUndefined()`. The check before it, that the built pool's `version` is `"v2"`, passed. Trace: `startedBefore` → `same(l.box)` compares lovelace, token and quantity only, `!known.some((p) => p.id === l.id)` holds until a look finds it, and `STARTED_SAID_MS` is 24 h.
- **Fix:** Record the set on each start (`version: "v2"` on every record 1.8.0 writes; none means 8131b1d's, as `FoundPool` already treats it), and have `startedBefore` match only records of the start's set (`l.version === "v2"`). That also keeps the next set apart when one comes.

### pr363#1

- **Severity:** low. **Kind:** test. **Introduced:** new.
- **Title:** The two copies' tests read a fixture pool that names no version differently, so the shown-rule fixture can't hold them to one meaning.
- **Where:** `seedelf-data/api/src/lovejoin/standard.rs:627-630`, `seedelf-platform/seedelf-web-wallet/extension/tests/lovejoin-discovery.test.ts:136`, `extension/tests/fixtures/lovejoin-shown.json:2`.
- **Claim:** The fixture says a pool's version "is tokenV1 (8131b1d's scripts, retired) when it names none". The extension's test reads it that way (no `version` → `valuesOf`'s `"tokenV1"`). The data layer's test reads a pool with no version as V2 ("v2's when none is given": only `"tokenV1"` is set to V1, on a V2 template pool). Every existing scenario either names no version on every pool or names each one, so both pass today. A scenario that mixes the two can't pass both, which is the cross-copy drift the fixture is there to catch. A typo such as `"V2"` would also diverge: tokenV1 in the extension, V2 in the data layer.
- **Scenario:** A future scenario lists an 8131b1d pool the plain way (no `version`) beside a later v2 pool of its values, expecting both shown, as the fixture's own rule says. The extension passes and the data layer fails. Expecting one shown does the reverse.
- **Evidence:** `python3 -I pr363-scripts/add_scenarios.py pr363-lovejoin-shown.orig.json <sandbox fixture> diverge` adds `{aaaa…: no version, 5 ₳ ADA, block 10; bbbb…: "v2", 5 ₳ ADA, block 20} → shown [aaaa…, bbbb…]`. Extension: `npx vitest run tests/lovejoin-discovery.test.ts --maxWorkers=2 -t "shows the earliest"` passes (1 passed). Data layer: `CARGO_TARGET_DIR=<scratchpad>/target-pr363-data cargo test --lib the_earliest_of_each_value_is_shown` fails: `left: ["aaaa…"]`, `right: ["aaaa…", "bbbb…"]`. The fixture was restored after.
- **Fix:** Read the version strictly and the same way in both tests: absent or `"tokenV1"` is V1, `"v2"` is V2, anything else fails the test. In `standard.rs`, `pool.derived.set = match p["version"].as_str() { None | Some("tokenV1") => Set::V1, Some("v2") => Set::V2, Some(other) => panic!("{other}") }`. Or name every pool's version in the fixture and have both refuse one that names none.

### pr363#2

- **Severity:** low. **Kind:** test. **Introduced:** new.
- **Title:** The data layer's new `version` on each listed pool is pinned by no test.
- **Where:** `seedelf-data/api/src/lovejoin/routes.rs:76`, `routes.rs:169`, `seedelf-data/api/src/lovejoin/templates.rs:41-46` (`Set::version`), `seedelf-data/README.md:129`.
- **Claim:** `lovejoin/pools` now serves `version` (`tokenV1` or `v2`), and the README documents it. Neither a constant `"v2"` in the route nor V1 named `"v2"` fails any offline test. The wallet doesn't read the field: it takes the set from WebAssembly's own verify. So a wrong value misleads only whoever reads the API, but it's a documented statement with nothing behind it.
- **Scenario:** A later edit swaps or hard-codes the name. Every 8131b1d pool is then listed as `v2`, and CI stays green.
- **Evidence:** Mutation D4 (`routes.rs:169` `version: p.derived.set.version(),` → `version: "v2",`) and D5 (`templates.rs:43` `Set::V1 => "tokenV1",` → `Set::V1 => "v2",`), each through `pr363-scripts/mutate.py` with `pr363-scripts/data-tests.sh` (`cargo test` offline, every binary, no `--ignored`): both exit 0 (lib 107 passed, edge 5, public_grammar 12, scripted_kupo 3). Logs: `pr363-mut/D4.log`, `pr363-mut/D5.log`.
- **Fix:** A unit test that builds the `PoolView` of a V1 and a V2 standard pool (e.g. `launch_in(Set::V1, …)` and `launch_in(Set::V2, …)` through `check`) and asserts `version`. Or hold `Set::version()` to WebAssembly's names (`"tokenV1"`, `"v2"`) through the shared vectors.
