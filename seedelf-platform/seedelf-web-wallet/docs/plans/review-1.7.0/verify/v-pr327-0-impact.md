# v-pr327-0-impact: impact and fix check of `pr327#0`

**Verdict: confirmed. Severity: low** (unchanged). This is not a code defect in any PR. It is a release-environment item for 1.7.0's step 1, to settle before `npm run tokens`, `dreps` and `lovejoin-pools` run. The fix is right and needs no repo change, guard or UI text. It needs two amendments (see *The fix*).

## The facts the finding rests on, re-checked on this box

- **The Node.** `command -v node` gives `~/.nvm/versions/node/v24.19.0/bin/node`. nvm's `default` is `lts/*`, which resolves to `lts/krypton` and then `v24.19.0` (alias files dated Aug 15). `NODE_OPTIONS`, `NODE_EXTRA_CA_CERTS`, `NODE_USE_SYSTEM_CA`, `SSL_CERT_FILE` and `SSL_CERT_DIR` are all unset. `node --help` says `--use-bundled-ca  use bundled CA store (default)`.
- **The stores.** Fingerprints are checked with `tls.getCACertificates`.

  | Mode | Certificates | ECC G3 (`86:A1:EC:BA…`) |
  |---|---|---|
  | default (= bundled) | 120 | trusted |
  | `--use-system-ca` | 482 | trusted |
  | `--use-openssl-ca` | 0 enumerable | not trusted |

  Under `--use-openssl-ca`, Node's `OPENSSLDIR` is `/etc/ssl`. There is no `/etc/ssl/cert.pem`, and `/etc/ssl/certs` has no link for G3's subject hash `14bc7599`. A real host (`api.github.com`) still verifies in that mode, whether the flag is given directly or through `NODE_OPTIONS`.
- **The OS store** (`ca-certificates 20260816ubuntu0.26.04.1`) has emSign G1, C1 and C3, and no G3. Neither the OS store nor Node's bundled one has "AAA Certificate Services".
- **Node's tags.** `src/node_root_certs.h` holds G3 at v24.19.0 and v24.22.0, and not at v24.22.1, v24.22.2, v22.23.4 or v26.13.0. It went out in `ae223417d964` "crypto: update root certificates to NSS 3.131.1" (2026-10-20), which also dropped C1 and C3 and kept G1.
- **The scripts.** `dreps.mjs:50` and `tokens.mjs:30` call Node's global `fetch` on `api.koios.rest` and `preprod.koios.rest`. `lovejoin-pools` runs through Vitest, whose `new Koios(...)` calls `fetch` too. They are the only network callers in `extension/scripts/`.
- **The output ships.** `src/ui/dreps.ts:7`, `src/ui/tokens.ts:13` and `src/background/lovejoin-pools.ts:57` import the files.
- **`npm ci` is safe.** All 101 entries in `package-lock.json` (lockfile v3) carry `integrity`.
- **The data layer's decimals refresh** (step 2's sub-bullet) is not exposed. `seedelf-data/scripts/token-decimals.py` only reads a local `git clone` of the registry, and git uses the system store.

## Reachability: more reachable than the finding says

The disclosure's own data (`emudhra.we-have-a-problem.com`, `roots.json` and `impacted-intermediates.json`) gives the path.

- **The TLS intermediates.** Six, `EM DV|OV|EV TLS CA - G3B|G3C`, are issued by *emSign Root TLS CA - G3*. That root is in Microsoft's store only. It is cross-signed by **emSign ECC Root CA - G3** (`role: cross_signer`, `mozilla: Included`). That is the anchor Node v24.19.0 bundles.
- **The Sectigo cross-signs** chain to *AAA Certificate Services* (`mozilla: Removed`, `chrome: Removed`). That root isn't in either store here, so G3 is the only path that matters on this box.
- **Revocation.** Each intermediate shows `revocation: revoked 2026-10-18, ca_compromise`. Node checks neither revocation nor Certificate Transparency.
- **The keys are not a barrier.** The disclosure says the keys "were incorrectly generated by the CA" and can be recovered from the certificates. The CPython thread (Heimes) says: "All 8 eMudhra CAs had private keys with d < 256". So the scenario's "an attacker … holds one of the eight compromised … keys … That's unlikely" overstates the hurdle. Anyone can have a key. **The only real precondition is being on-path**, or controlling DNS, between the dev box and Koios while a refresh runs: the LAN, the router, the ISP or a transit network.
- **Small correction.** The claim's "(and C1, C3)" isn't part of this incident. The disclosure names ECC G3 as the only emSign cross-signer, and Ubuntu's patched store keeps C1 and C3.
- **It has already run once in the window.** 1.6.0's DRep list and pools head start were refreshed on 2026-10-25 (`8cd8ce08`). That is after the 10-17 report and the 10-20 public disclosure. It was almost certainly on v24.19.0: 1.6.0's package line in `roadmap.md:63` says "Node 24.19.0", and it's the box's only 24.x. The token registry wasn't changed by that run.

## Impact: real, bounded, and in diffs the owner reads

- **DReps.**
  - `dreps.mjs:99-112` keeps the first name any pass gives. A committed name survives only when no pass names the DRep. So a forged rename gets through, as the finding says.
  - With an honest list, an impostor that copies a name gets `shared = 2`, and the `.warn.` callout shows (`Voting.tsx:444-448`, `495` `shared > 1`). If the forged list renames the real DRep, `shared = 1` and the callout stays silent. A name search then finds only the impostor.
  - The harm is misdirected vote delegation. No funds move, and the user can change it.
- **Tokens.**
  - The ticker is checked (`tokens.mjs:87-89`). Name, decimals and logo are taken from the answer (`94-99`), and `tokenDecimals` prefers the list's value (`tokens.ts:66-68`). So a forged decimals value mis-scales every form for that token. A balance shown 10^k off would be visible to the user.
  - The logo is re-encoded through a canvas into WebP, so no payload survives.
  - The owner reads a 32-entry diff (`development.md:273`).
- **Pools.**
  - Money is safe. A deposit into a pool that was never launched is refused by the ledger, because "every transaction into a token pool reads its reference UTxO" (`lovejoin-pools.ts:33-36`).
  - The finding's "never a gate" is slightly too strong, though. Head-start pools enter a device's pool set unconfirmed (`lovejoin-pools.ts:349-351`). A forged *earlier* launch of the same values would then win `shown()` (`166-173`). That hides the real pool on new devices of that release: a denial, not a loss.
  - The refresh rebuilds the file from the holder's start, so the diff would show the real pool dropped.
- **Trust.** The refreshes already trust whatever Koios answers (a gateway in front of community instances). The CA gap widens who can tamper, from Koios's operators to anyone on-path, until the box's Node is fixed.
- **Why low.** No money is lost or locked. The attack needs an on-path attacker during the refresh, and then an odd diff the owner misses. That fits the brief's "low", not "medium". It isn't "owner-call": no product decision is involved, just release hygiene before step 1. Whether `development.md` should name a minimum Node is the owner's call, as the finding says.

## The fix: right, with two amendments

1. **`nvm install 24` alone leaves new shells without `node`.**
   - Node 26.13.0 became LTS ('Lithium') today. `nvm install 24` reads the remote index, and nvm 0.39.5's `nvm_ls_remote_index_tab` rewrites every LTS alias each time. So `lts/*` will then name `lts/lithium`, which is v26.13.0 and not installed. The box's `default` is `lts/*`.
   - Simulated offline with a copy of `nvm.sh` and those aliases: a new shell gives `resolve default -> N/A` and `node on PATH: none`. After `nvm alias default 24` it gives `v24.22.2`.
   - So the line is `nvm install 24 && nvm alias default 24`.
   - Don't use `nvm install --lts` for this release. It gives 26.13.0, and `development.md:287` vouches only for "Official Node builds 20 to 24" zipping alike.
2. **This release's diff also checks 1.6.0's 10-25 run.** On a fixed Node, `npm run lovejoin-pools` rebuilds the head start from the holder's start, and `npm run dreps` asks for every DRep again. So anything the 10-25 run could have taken is replaced, except DRep names kept as committed. The script's output line counts those.

`NODE_OPTIONS=--use-openssl-ca` is a valid no-install alternative here. It works through the Vitest worker that `lovejoin-pools` uses. A scratch test, now deleted, gave:
- plain: `default=120 G3=true`
- with the flag, in the forked worker: `default=0 G3=false github=200`

It relies on Ubuntu's store being current, which it is, and it covers only the commands it's put on. The newer Node covers every Node TLS use on the box, `LIVE_KOIOS` and `e2e/live` included. `--use-system-ca` is not a fix: it adds the OS store to the bundled one, so G3 stays trusted.

Paste-as-is, on the dev box, before step 1's refreshes:

```bash
hostname
nvm install 24 && nvm alias default 24 && node --version
node -e 'const {X509Certificate}=require("crypto");const g3=require("tls").getCACertificates("default").some(p=>new X509Certificate(p).fingerprint256==="86:A1:EC:BA:08:9C:4A:8D:3B:BE:27:34:C6:12:BA:34:1D:81:3E:04:3C:F9:E8:A8:62:CD:5C:57:A3:6B:BE:6B");process.exit(g3?1:0)' && echo "no G3: run the refreshes"
```
