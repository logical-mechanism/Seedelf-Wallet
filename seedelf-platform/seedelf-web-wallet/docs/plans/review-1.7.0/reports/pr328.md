# PR #328: rustls 0.23.46 in `seedelf-platform/Cargo.lock` (label `pr328`)

Merge `641f751c` (head `a911658c`, base `8d876588`). Reviewed on HEAD `6bca8bec`.

## Verdict

The PR does exactly what it says. It changes one lockfile entry, rustls 0.23.45 → 0.23.46 (version and checksum, `seedelf-platform/Cargo.lock:2270-2273`). No compiled code changes on any target, and it clears Dependabot #100–#103. I found no defect in the PR.

What it leaves open sits outside Dependabot's view: RustSec-only advisories in the wallet's own graphs. There are two nits, below (N1, N2), neither a release blocker. The CLI-only matters are under *CLI notes*.

## Findings

### N1 · nit · security: the data layer's lock carries ctutils 0.4.3 (RUSTSEC-2026-0385) and tokio 1.53.2 (RUSTSEC-2026-0386), which Dependabot never raises

**Evidence**

- `seedelf-data/Cargo.lock:275-276`: `name = "ctutils"` / `version = "0.4.3"`.
- RUSTSEC-2026-0385, dated 2026-10-23: "Non-constant-time mask generation and `u128` comparisons", patched at `>= 0.4.4`.
- GitHub's global database has no entry for ctutils (`gh api "/advisories?ecosystem=rust&affects=ctutils"` returns nothing). So no Dependabot alert will ever come.
- The path, from `cargo tree -i ctutils` in `seedelf-data`: ctutils ← `digest` 0.11.3 ← `hmac` 0.13.0, `md-5`, `sha2` ← `postgres-protocol` 0.6.12 ← `tokio-postgres` 0.7.18 ← `deadpool-postgres`, `seedelf-data-api`.
- ctutils' only use there is `digest-0.11.3/src/mac.rs:144`: `let choice = self.finalize_fixed().as_slice().ct_eq(tag);` (the `Mac::verify*` family).
- That is reached from `postgres-protocol-0.6.12/src/authentication/sasl.rs:300`: `hmac.verify_slice(&verifier)`, the SCRAM check of the server's signature.
- `seedelf-data/deploy/home/pg_hba-seedelf.conf` shows the API logs in with `scram-sha-256`.
- `seedelf-data/Cargo.lock:1250-1251`: `tokio` `1.53.2`, under RUSTSEC-2026-0386 (informational, unsound): the `AsyncFd::{new,with_interest,try_new,try_with_interest}` constructors. It is patched at `>= 1.53.3`.
  - No crate among the data layer's 175 registry crates calls those constructors, and neither does `api/src`.
  - 1.54.0 is yanked (GHSA-5wjr-9356-4wc8).
- `cargo deny check advisories` in `seedelf-data` against the current database flags both.

**Scenario**

1. Every new pooled connection from the API to home's Postgres runs SCRAM, and postgres-protocol checks the server's signature with ctutils' constant-time compare. On 0.4.3 that compare may branch.
2. Only the party sending the signature can time it: home's Postgres, or someone on the WireGuard path.
3. The value compared, HMAC(ServerKey, AuthMessage) over the client's fresh nonce, changes on every connection, and a failed check closes the connection. That gives one guess per value, nothing to accumulate, and no key exposed.

There is no harm today. The cost is a RustSec report that isn't clean, for advisories no Dependabot alert will surface. tokio's unsound constructors have no caller.

**Fix:** with the next data-layer change, through the deploy workflow:
- In `seedelf-data`, run `cargo update -p ctutils` (0.4.3 → 0.4.6; one entry, same `cmov ^0.5.3`).
- Run `cargo update -p tokio --precise 1.53.3` (or 1.54.1, never the yanked 1.54.0).

**Test:** `cargo deny check advisories` in `seedelf-data` against a current RustSec database flags both before the fix and passes after. data-layer.yml's `cargo test --locked` stays green.

**Confidence:** high, both that the advisories apply and that there's no exposure.

### N2 · nit · docs: *Step 0*'s record of what Dependabot doesn't raise is behind

**Evidence**

- `docs/post-release-roadmap.md:93` says rustls is "now 0.23.45" and that "What's still open is the CLI's `h2` and `spin` …, which Dependabot doesn't raise".
- `:89` describes `rand` as "the only flagged crate that reaches what users install".
- But the lock has rustls 0.23.46 (`seedelf-platform/Cargo.lock:2271`), which `:35` records only as "(#328)".
- RustSec now flags `crypto-bigint` 0.5.5 in the shipped module: RUSTSEC-2026-0387, dated 2026-10-23, patched at `>= 0.7.6` only (`Cargo.lock:475-476`).
  - The path, from `cargo tree -p seedelf-wasm --target wasm32-unknown-unknown -i crypto-bigint`: crypto-bigint 0.5.5 ← elliptic-curve 0.13.8 ← ecdsa 0.16.9 and k256 0.13.4 ← uplc 1.1.23 ← seedelf-core ← seedelf-wasm.
  - It is in the `wasm-release` unit graph, and the module holds `crypto-bigint-0.5.5/src/uint/encoding.rs`.
- `uplc-1.1.23/Cargo.toml:150-153` uses `secp256k1` natively and `k256` on wasm. `src/machine/runtime.rs:1967,1980` uses only `k256::{ecdsa,schnorr}` `PrehashVerifier`: verification of public signatures in the local script evaluator.
- No Seedelf code uses secp256k1 (`git grep -E 'k256|secp256k1'` finds nothing).
- GitHub's database has no crypto-bigint advisory.

**Scenario:** the next release's triage reads *Step 0*, the section that tracks what Dependabot doesn't raise. It learns that rustls is at 0.23.45 and that only the CLI's h2 and spin are open. It doesn't learn about:
- the four advisories #328 cleared;
- that the module now carries a RustSec-flagged crate. That crate is harmless: its timing issues need secret inputs, and k256 here only verifies public signatures. It also can't be fixed in 0.5.x, so it waits on a uplc that moves to k256 0.14;
- the data layer's two (N1).

**Fix:** one sentence in *Step 0* after "now 0.23.45", with no release date and no store status:

> #328 took it to 0.23.46 for RUSTSEC-2026-0346 to -0349 (Dependabot #100–#103), still never built. RustSec, which Dependabot doesn't read, also flags `crypto-bigint` 0.5.5 in the WebAssembly (RUSTSEC-2026-0387, through uplc's `k256`, which only verifies public signatures; no 0.5 fix), and the data layer's `ctutils` and `tokio`.

**Test:** none (docs).

**Confidence:** high that the paragraph is behind. Whether that history is kept current is the owner's call.
