# pr335: Transaction details for every part (PR #335, merge `0bad0d52`)

## Summary

PR #335 adds a stepper ("‹ Transaction 1 of 2 ›") to the transaction view of a review in parts. It also makes `tx-view.ts` follow the first part's `partHashes` to `<key>.<i>`.

**Verdict: it does what it says, and it's sound.**

- **The worker's lookup:**
  - It is scoped to the record's own key, and to the part's own `network` (every part record carries one, through `summaryOf`).
  - It ignores hash case and reads only session storage, so Koios is never asked.
  - It can't serve wrong bytes, because `cborOf` checks the part record's own `txHash`.
- **The five reviews that can go in parts** all pass `parts`: Send, Make public, a swap's funding, Lovejoin's private mix and a site's funding. No other review can go in parts: a top-up, a collateral top-up, Mix again and a Bootstrap are built with `inParts: false`, and a return or a chain is one transaction.
- **The worker test fails without the new lookup.** I checked this by mutation in a copy, and it fails with exactly the NOT_HELD error the PR names.
- **Strings:** the three new keys pass the i18n guards. The word order is right in es ("Transacción {{n}} de {{total}}") and ja ("全 {{total}} 件中 {{n}} 件目", the house pattern of `lj.step.transaction`). Neither key is critical, and provenance is recorded.
- **No later PR (#336, #337) touches the view or the parts.**

There are 2 low findings, 1 low test gap and 3 nits. Nothing touches money or privacy.

## Findings

### 1. low · correctness/ux: the stepper's index outlives a review rebuilt in place, giving "Transaction 3 of 2" over the first part

**Where:** `extension/src/ui/components/TxDetail.tsx:125-127, 159, 165`. The modal is mounted by `TxDetailButton` (`:68`, `:77-78`) with no key.

**What's wrong:**
- `shown` is the modal's own state. Nothing resets or clamps it when `parts` or `txHash` change.
- `TxDetailButton` keeps `open` across a re-render of its review, so an open modal outlives a rebuild of that review.
- `hash = many?.[shown] ?? txHash` then falls back to the new first's hash, while the label says `shown + 1` of `many.length`.
- Next is disabled only at exactly `shown === many.length - 1`, so it stays live past the end.

**Scenario:**
1. A Make public in 3 parts is refused at Send as stale.
2. "Refresh and review again" builds in place (`StaleReview.tsx:97`, `Withdraw.tsx:129`). The review and its *Transaction details* chip stay on screen and clickable while the parts are built and measured, which takes seconds.
3. The user opens the details and steps to "Transaction 3 of 3". The worker still holds the old records until the new build's `keepParts`.
4. The new review comes back in 2 parts. The open modal now reads "Transaction 3 of 2" over the new first transaction, with both arrows enabled. Next goes on to "4 of 2", "5 of 2", and so on.

The same in-place rebuild happens in the other four reviews:
- a swap's switch or Change, at `Swaps.tsx:838`;
- `buildAgain` after a refusal, at `Lovejoin.tsx:2984`;
- `dapp-private-build`'s build again, at `DappApprovals.tsx:659`;
- Transfer's stale foot.

No money is at risk: Send is behind the modal, and Send never reads the view.

**Evidence:** a scratch SSR render of the real `TxDetailModal`, with `shown` preset to 2 and `parts` of 2, gives:
```
<output class="stepper__value" data-testid="tx-part">Transaction 3 of 2</output>
```
That render has no `disabled` on either button, and `data-value` is the first hash.

**Fix:** clamp the index, for example `const at = many ? Math.min(shown, many.length - 1) : 0`, used for the hash, the label and both ends (`disabled={at >= many.length - 1}`). Also key the modal by the review's first hash (`<TxDetailModal key={txHash} …/>`), so a new review opens on its first transaction.

**Test:** an SSR test with the index preset past the parts, as above, expecting "Transaction 2 of 2" and Next disabled. It fails before the clamp and passes after.

**Confidence:** high. The code, React's state semantics and the scratch render all agree.

### 4. nit · tests/ux: after Next, the e2e's checks aren't tied to the second part's read

**Where:** `TxDetail.tsx:132` clears the view inside the effect, not as the index changes. The e2e is at `extension.spec.ts:2669` and `:2672`.

**What happens:**
- Inside the effect, the clear runs at default priority. So there is one committed state where the label already reads "Transaction 2 of 2" while the body and the id are still part 1's.
- The e2e's `toContainText("Pays")` after Next can match that stale body.
- `not.toHaveAttribute("data-value", first)` passes on the loading state too.
- `withdraw-tx-error` `toHaveCount(0)` can then run before part 2's answer arrives.

**Scenario:** with the lookup broken for later parts, a run where Playwright's check lands before React's clearing render passes anyway. In practice React usually wins, and the author saw the e2e catch the bug.

**Fix:**
- In the test, wait for `withdraw-tx-loading` to have count 0 after the id changes, then check the error. Or check a fact only part 2 has.
- In the component, render the body only when the view's own hash equals `hash`.

**Confidence:** medium.

### 5. nit · a11y: keyboard focus drops to `<body>` when the focused arrow disables itself at an end

**Where:** `TxDetail.tsx:152` and `:165`, the same pattern as the box stepper (`Lovejoin.tsx:3232-3238`).

**Scenario:** a keyboard user presses Enter on Next at "1 of 2". The arrow disables itself, and focus goes to `<body>`. Enter and Space then do nothing until they press Tab.

**Evidence:**
- I checked this in Chromium 153 with a `showModal()` dialog: `activeElement` was BODY.
- Tab then went to the next control and Shift+Tab to Previous, so Chrome keeps the starting point. Escape still closes.
- The labels are right: the arrows have aria-labels, the SVG is aria-hidden, and `<output>` is a polite live region.

**Fix (owner's call, kept as the box stepper has it):** keep the arrows focusable with `aria-disabled`, or move focus to the other arrow on reaching an end.

**Confidence:** high on the behaviour. Whether it's worth changing is the owner's call.

### 6. nit · ux: during Send, and after a part fails, every part reads "isn't one the wallet is holding. Review it again."

**Where:**
- `pending.ts:524` removes the first part's record as the watch takes it. That record is the only one that names the parts.
- `tx-view.ts:158` follows the parts only from that record.
- `holdWaiting` moves waiting parts to `seedelf.waitingPart.<hash>`, which the view never reads.

**Scenario:**
1. A Make public in 3 parts is sent. The details chip isn't disabled while Send is busy.
2. While part 2 goes (giveme.my, then Koios), the user opens the details.
3. All three parts read "That transaction isn't one the wallet is holding. Review it again." That includes part 3, still kept under `seedelf.withdraw.built.2`.

**Why it's only a nit:**
- Before the PR, part 1 read the same.
- After a partial failure (`worker.parts.partly`), "Review it again" is the right advice.
- No screen offers the view after a successful Send.

**Fix:** none needed for the release. Optionally, disable the chip while a review is sending.

**Confidence:** high.
