# PR #338: review (label `pr338`)

**PR:** #338, merge `6bca8bec`, "docs(web-wallet): 1.7.0's item 8, the Leios run on Musashi, done". Docs only: 6 lines changed in `docs/post-release-roadmap.md`. Item 8 is ticked (:42), and its *Kept in mind* plan is replaced with what the run found (:405–409). The run's branch, `web-wallet/leios-musashi`, was read only (`git show`), never checked out.

## Verdict

Nothing ships from this PR: no code, no strings, no store text. Most of what the entry says holds.
- **Against the ledger:** I checked the ledger's own source (read-only `gh`). From PV 12, the redeemer decoder fails on the list form: `Alonzo/TxWits.hs`, "List encoding of redeemers not supported starting with PV 12". Dijkstra's certificate decoder refuses tags 0 and 1 and keeps 2 and 7 onwards: `Dijkstra/TxCert.hs:241`.
- **Against core:** `withdraw_zero.rs` and `pallas-txbuilder` 0.35.1 both write `Redeemers::List`. `launch.rs` writes `Certificate::StakeRegistration`, which is certificate 0. Lovejoin's `mix_logic` publish allows `RegisterCredential` only.
- **Against the run's records:** I recomputed every row of the README's live table from the 20 run records. 96 of 248 timing-eligible EBs were certified (38.7%). Both 2.8× and 5.6× follow from the harness's own formula.
- **The house rules:** the entry dates no release and states no store status. "much later" is the owner's own phrase (recorded 2026-10-28), not a date.

Four things are wrong or missing:
- **The window.** "A chain's window of four in flight" is two for four-box chains. The "120 to 245 s more" is a second wave's own wait, not a saving the runs measured.
- **The coverage.** "Mended, all of it ran on Musashi" includes withdraws, and none was sent.
- **The fix.** "A Pallas update, *or* patches in core" undersells core's part:
  - core's own patch writes a list, and refuses a map;
  - Pallas can stage no certificate;
  - no Pallas release writes a map yet.
- **CIP-30.** The entry's list of what Leios would change omits it. Pallas 0.35's Conway decoder refuses Dijkstra's three-element transaction shape, and that decoder is what the wallet reads a site's transaction with. I ran a scratch test to confirm it.

At the interaction level, items 4–7 are still unticked on HEAD, and #338 ticked only its own item. That is agreed (#333: "the 1.7.0 list's tick waits for the release-prep docs commit"). The *Kept in mind* lines for item 5 still describe requests the wallet doesn't make.

### 4. low · docs: "What Leios would change in the wallet" leaves out CIP-30, whose decoder refuses Dijkstra's own transaction shape (confidence: high on the code, medium on relevance)
- **Files:** `docs/post-release-roadmap.md:409`; `seedelf-web-wallet/wasm/src/cip30.rs:1029-1030`; `seedelf-web-wallet/wasm/src/decode.rs:633-634`
- **Claim:** The wallet reads a site's transaction (CIP-30 `signTx`) and shows it in Transaction details with Pallas 0.35's Conway decoder. That decoder refuses Dijkstra's three-element shape, `[body, witnesses, auxiliary data]`, which the run saw IO's load use. It also can't read Dijkstra's new fields.
  - The run's README says the decoding gap "only meets it where it reads others' from the chain".
  - That misses CIP-30, where the transaction comes from a site, not the chain.
  - The roadmap's entry drops the point altogether.
- **Scenario:**
  1. Mainnet reaches Dijkstra.
  2. A dApp whose library emits Dijkstra's shape asks for a signature.
  3. The wallet answers "The wallet can't read this transaction: unexpected type null at position 9: expected bool" and can't sign it or show its details.
- **Evidence:**
  - `cip30.rs:1029`: `let tx = conway::Tx::decode_fragment(&bytes).map_err(|e| anyhow!("The wallet can't read this transaction: {e}"))?;`
  - `decode.rs:633`: `let tx = conway::MintedTx::decode_fragment(&bytes)…`.
  - The scratch test (`seedelf-core/tests/zz_review_pr338_1.rs`, since deleted) decoded `[{0:[],1:[],2:0}, {}, true, null]` fine, and refused `[{0:[],1:[],2:0}, {}, null]` from both `conway::Tx` and `conway::MintedTx` with "unexpected type null at position 9: expected bool".
  - Pallas 0.35's `PseudoTx` has `#[n(2)] pub success: bool`.
  - Branch README: "Dijkstra still takes it for a transaction sent to a node, beside its own three-element shape ([body, witnesses, metadata], which IO's load used)."
- **Fix:** Add one clause to :409: "CIP-30 signing and Transaction details read a site's transaction with Pallas's Conway decoder, which refuses Dijkstra's three-element shape and its new fields."
