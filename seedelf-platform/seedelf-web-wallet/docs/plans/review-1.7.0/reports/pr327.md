## Findings

### 1. low (security): the release-time list refreshes fetch Koios through a Node that still trusts emSign ECC Root CA - G3

**Files:**
- `seedelf-platform/seedelf-web-wallet/extension/scripts/dreps.mjs:50`
- `seedelf-platform/seedelf-web-wallet/extension/scripts/tokens.mjs:30`
- `seedelf-platform/seedelf-web-wallet/extension/tests/lovejoin-pools-head-start.test.ts:63`
- `seedelf-platform/seedelf-web-wallet/extension/package.json:19-21`
- `seedelf-platform/seedelf-web-wallet/docs/development.md:183-185`

**Claim.** #327 closes the advisory for the happy-path Python. Its body accounts for pip's store and the Rust crates' store, but not Node's.
- Node compiles in its own Mozilla store and uses it by default.
- The dev box's Node is v24.19.0 (nvm's default `lts/*`). No `NODE_OPTIONS`, `NODE_EXTRA_CA_CERTS` or `NODE_USE_SYSTEM_CA` is set.
- That Node still trusts emSign ECC Root CA - G3, the root the advisory is about. It also trusts C1 and C3. The OS store and certifi 2026.10.23 no longer trust G3.

The three refreshes run at every release (`npm run tokens`, `npm run dreps`, `npm run lovejoin-pools`):
- They fetch `api.koios.rest` and `preprod.koios.rest` with Node's `fetch`.
- They write files that ship in the extension: `src/tokens/registry.<network>.json`, `src/dreps/<network>.json` and `src/lovejoin-pools.json`.
- Node doesn't check revocation, so revoking the eMudhra intermediates doesn't protect these fetches.

This isn't a code defect in any PR. It's a gap in the environment at the release step this review gates.

**Scenario.**
1. During 1.7.0's release prep on the dev box (`which node` → `~/.nvm/versions/node/v24.19.0`), the owner runs `npm run dreps` (development.md, step 3).
2. An attacker on the network path to `api.koios.rest` holds one of the eight compromised eMudhra intermediate keys. They present a certificate for `api.koios.rest` that chains to G3, and Node accepts it.
3. Their forged `drep_metadata` answers give a well-known DRep a new name and give that DRep's old name to the attacker's DRep. The script writes the result to `src/dreps/mainnet.json`. It keeps a committed name only for a DRep that no pass names, so a rename gets through.
4. If the owner's diff skim misses the rename, 1.7.0 ships a list where searching that name finds only the attacker's DRep. The live card's shared-name warning (`drepSharing` in Voting.tsx) counts names on the bundled list, so it stays silent when the attacker's live metadata uses the same name.

The token refresh is a narrower target. The ticker must match the list (`tokens.mjs:10`), but decimals, name and logo come from Koios's answer. The owner reads that diff. The pools file is never a gate: the wallet verifies every pool.

The attack needs an attacker on the network path, holding a compromised key, at the moment of the refresh. That's unlikely. Still, it's the advisory's exact threat, on the one Node path whose output ships.

**Evidence.**
- `node --help`: `--use-bundled-ca  use bundled CA store (default)`.
- `tls.getCACertificates("default")` on v24.19.0 holds G3. Its SHA-256 fingerprint is `86:A1:EC:BA:08:9C:4A:8D:3B:BE:27:34:C6:12:BA:34:1D:81:3E:04:3C:F9:E8:A8:62:CD:5C:57:A3:6B:BE:6B`, and the test below exits 1.
- `--use-system-ca` doesn't help. It *adds* the OS store (bundled 120 + system 362 = 482), and G3 is still trusted.
- `nodejs/node` `src/node_root_certs.h`:

  | Tag | G3 present? |
  |---|---|
  | v24.19.0 | yes |
  | v22.22.3 (installed here) | yes |
  | v24.22.1 | no |
  | v24.22.2 | no |
  | v22.23.4 | no |
  | v26.13.0 | no |

- `/etc/ssl/certs/ca-certificates.crt` (ca-certificates `20260816ubuntu0.26.04.1`) has no G3. It has emSign G1, C1 and C3.
- `scripts/tokens.mjs:24` `const KOIOS = { preprod: "https://preprod.koios.rest/api/v1", mainnet: "https://api.koios.rest/api/v1" };`, then `:30` `const response = await fetch(url, {`. It writes at `:103`.
- `scripts/dreps.mjs:29` (same hosts), then `:50` `const response = await fetch(url, {`, and `:125` `writeFileSync(\`${dir}${network}.json\`, body);`.
- `tests/lovejoin-pools-head-start.test.ts:63` `koios: () => new Koios(NETWORKS[network].koios),` leads to `src/background/koios.ts:767` `(url, init) => fetch(url, init)`. `vite.config.ts:145` sets `environment: "node"`.
- `docs/development.md:183-185` runs `npm run tokens`, `npm run dreps` and `npm run lovejoin-pools`. Lines 273 and 275–276 make them steps at every release.
- `src/ui/tokens.ts:13` `import mainnet from "../tokens/registry.mainnet.json";` and `src/ui/dreps.ts:7` `import mainnet from "../dreps/mainnet.json";`.
- Not the npm install: all 101 lockfile packages carry `integrity`.

**Fix.** No repo change. Before 1.7.0's refreshes, either:
- Move the release box to a Node whose built-in store dropped G3: v24.22.1 or later (`nvm install 24` gives v24.22.2), or v22.23.4 or v26.13.0 (checked at those tags).
- Or run the three refreshes with `NODE_OPTIONS=--use-openssl-ca`. Node then uses OpenSSL's store, the OS's, which here has no G3. I checked that a real host still verifies in that mode.

Don't use `--use-system-ca`: it adds the OS store to the bundled one, and G3 stays trusted (checked). Whether development.md's release steps should also name a minimum Node is the owner's call.

**Test.** Run on the release box before the refreshes. It exits 1 on v24.19.0 today, and 0 on v24.22.1 or later:

```
node -e 'const {X509Certificate}=require("crypto");const g3=require("tls").getCACertificates("default").some(p=>new X509Certificate(p).fingerprint256==="86:A1:EC:BA:08:9C:4A:8D:3B:BE:27:34:C6:12:BA:34:1D:81:3E:04:3C:F9:E8:A8:62:CD:5C:57:A3:6B:BE:6B");process.exit(g3?1:0)'
```

**Confidence:** high that the gap exists. The attack itself is unlikely.

## CLI and contracts notes (not the wallet)

1. **The pin is verified.**
   - The certifi 2026.10.23 wheel's hash matches PyPI. Its bundle has 118 roots, down from 151, and no G3 by label, fingerprint or public key.
   - 2026.10.18 dropped every emSign root. 2026.10.19 restored G1, C1 and C3. 2026.10.23 dropped C1 and C3 again, so G1 is the only emSign root left.
   - 45 roots left between the two pins (Entrust, Baltimore, legacy DigiCert, GlobalSign R1, Go Daddy and Starfield class 2, and others), and 12 arrived. The roots a host like Koios chains to (ISRG X1 and X2, GTS R1 and R4, DigiCert G2, USERTrust, Amazon) are all still there.
2. **The owner's own happy-path venv still holds certifi 2024.8.30 (G3 included), but it no longer works anyway.**
   - It's `seedelf-contracts/happy-path-scripts/seedelf/backend/venv`, gitignored, built in December 2024 on Python 3.12.3.
   - `/usr/bin/python3.12` is gone, and the venv's `python3` now runs 3.14.4, which sees no site-packages there. The scripts would stop at `import cbor2` or `import requests` before any TLS.
   - Running `bash setup.sh` in `backend/` again rebuilds it on 3.14 with the new pins.
3. **`setup.sh`'s own install has no hash pins.** It trusts whatever store the venv's pip uses.
   - With pip 24.2 or later on Python 3.10 or later, that's the OS store, through truststore. I confirmed this in pip 25.1.1's `index_command.py`: truststore unless `legacy-certs` is set, disabled below 3.10.
   - Ubuntu's pip also points its vendored certifi at `/etc/ssl/certs`.
   - A venv whose ensurepip pip is older than 24.2, on another OS, would check PyPI against pip's vendored certifi, which includes G3.
   - An optional hardening is `--require-hashes`.
4. **The PR body's Rust claim holds.**
   - Neither `Cargo.lock` has `webpki-roots`, `rustls-native-certs` or `rustls-platform-verifier`.
   - `seedelf-koios` and `seedelf-display` use reqwest 0.12.22 with native-tls, which is OpenSSL with the OS store. On this box the OS store has no G3.
   - rustls 0.23.46 (#328) comes in through reqwest's `hyper-rustls`, with no roots of its own.
   - The CLI on other machines trusts whatever their OS store holds.
   - The data API's reqwest is `default-features = false`: plain HTTP to home over WireGuard.
5. **`query.sh` calls giveme.my with `curl`,** which uses the OS store, so certifi doesn't affect it.
