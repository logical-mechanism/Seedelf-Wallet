# PR #336 review (label `pr336`)

**PR:** #336, merge `473b7f1a` (commit `f40ed2fc`). A pool the data layer lists is confirmed from Koios first (`confirmed()` → `launched()` in `extension/src/background/lovejoin-pools.ts`), with a privacy policy entry. Item 5 of 1.7.0's list.

## Verdict

The PR does what it says for the two facts it names. On mainnet, a pool the data layer lists that's new to the device is kept only once Koios's `tx_info` shows its launch spent the seed, and L was registered by the launch or an earlier block. Both paths run that check through one method, `launched()`.

- **Rate limit:** the requests use `koiosAlone()`, a plain Koios client on the shared `KOIOS_LIMIT`.
- **When the check runs:** preprod, Koios-only and a down private part never reach `confirmed()`, because `privateIndexClient` returns nothing there. So nothing is asked twice.
- **Remembered:** a kept pool is never asked about again. The record is in local storage, so it survives a lock and is kept per network.
- **Koios down or 429:** the pool waits for the next list, and no kept pool is lost.
- **Same rule as the data layer:** the block-level comparison (`block_time < tx_timestamp`) matches the data layer's `block < launch.block`.
- **Request shapes:** they match recorded live Koios answers (flat `account_update_history` rows; `tx_info` certificates typed `stake_registration` with `info.stake_address`).
- **Tests:** the new tests fail without the check (mutations M1 to M4).

**Docs:** the policy's pools paragraph, its 28 October entry and the *Effective* line are in, and privacy.md matches.

**What it leaves open, all low:**
- **F1:** the pool's reference row (its datum: box ADA, token, max fee) and its launch position are still the server's word. `tx_info` is asked without outputs, and the scripts derive from the seed alone.
- **F2:** a pool read now waits through Koios's retries while a new pool is unconfirmed.
- **F3:** on a device with no record yet, each pool read during that wait sends the check again.
- **F4:** the device that started a pool is likely the first to ask Koios about it.
- **F5:** `confirmed()`'s trap rethrow has no test.
- **F6 to F8:** stale docs.

Nothing high or medium.

**What a Koios operator learns, and when.** From the user's IP address, at the first non-quiet pool read after the data layer lists a pool new to this device: the launch hashes of every such pool, and rarely an L stake address. A non-quiet read is the hub's status, a mix's or return's build, a named pool, or `madeBy`. It happens at most once every 5 minutes in a worker's life, and again at each worker start while a pool is unconfirmed. From that, Koios can tell:
- this IP runs Seedelf Wallet's Lovejoin, and read pools at that moment;
- which pools were new to the device, which hints at when it last read;
- for a pool the user just started, likely that they started it (F4).

## Findings

### F1 (low): `confirmed()` checks the launch with Koios but keeps the server's row and position

- **Where:** `lovejoin-pools.ts:576` (`fresh.map((p) => ({ row: p.ref.reference, scripts: p.ref.scripts ?? [] }))`), `:582-583` (returns the server's `found` entries); `koios.ts:942` (`select=tx_hash,block_height,tx_block_index,tx_timestamp,inputs,certificates`: no outputs); `seedelf-core/src/lovejoin/templates.rs:120-127` (`derive(seed)`: policy, then `mix_logic`, then `mix_box`, with no box value); `private-index.ts:393-401` (`utxoOf` takes the address, value, datum and assets from the server's row).
- **Claim:** a pool's scripts derive from its seed alone, so nothing offline pins the reference datum's box ADA, token or max fee.
  - `launched()` runs on the server's reference row, and Koios is asked only for the transaction's inputs and certificates. Koios confirms that the launch exists and spent the seed, but never the row itself.
  - The launch position is the same: `launched()` builds the pool with Koios's block and index, then `confirmed()` returns the server's (which `shown()`'s order reads).
  - So "as the holder's look would" and "so devices can't disagree" don't hold against a lying server. The holder look reads the row from Koios.
- **Scenario:** a compromised data layer lists pool A's real reference outpoint (launch T, seed S, L registered by T) with a datum saying 3 ₳ a box, where the chain says 2 ₳.
  - A device new to A keeps it after one `tx_info`. Its hub shows 3 ₳ boxes.
  - A Bootstrap from that device puts up to 96 boxes of 3 ₳ into A's real `mix_box`. Its reference input is A's real reference UTxO, so the ledger takes the deposit; no script runs on a deposit.
  - No mix can ever take those boxes: the Mix branch forces outputs at exactly the datum's value. They come back only by hand, through the Owner branch (proofs alone, Lovejoin 8131b1d `validate_owner`), at both fees, with the deposit tied to its way back.
  - A device on the holder path keeps the true 2 ₳.
- **Evidence:** a scratch test in a copy:
  - With the datum changed from `1a001e8480` to `1a002dc6c0`, discovery sent one `tx_info` and kept the pool with `boxLovelace: "3000000"`.
  - With the server saying block 1, place 0 and Koios saying `BLOCK`, place 3, the pool was kept at `{ block: 1, index: 0 }`.
- **Fix:**
  - In `confirmed()`, read the fresh reference outpoints from Koios: `koios.utxoInfo(refs)`, 60 a request, which is the request the roadmap's `pool-exists` entry proposed.
  - Run `launched()` on Koios's rows, and keep `launched()`'s pools: Koios's row, seed and position. Or drop a pool whose server row or position differs.
  - It costs one more request per batch, the same for every wallet. The policy entry would name it.
- **Test:** a listed pool whose reference datum differs from Koios's row isn't kept, or is kept with Koios's values. One whose launch block differs keeps Koios's.
- **Confidence:** high for the mechanism, medium for the harm.

### F2 (low): a pool read on mainnet waits through Koios's retries while a newly listed pool is unconfirmed

- **Where:** `lovejoin-pools.ts:454` (`await this.keep(network, await this.confirmed(network, found))`), `:597-601` (`serviceDeps.pools` awaits `refresh`), `:570`; `koios.ts:421`, `:429` (`TIMEOUT_MS = 45_000`), `:1371-1376`; `data-layer.ts:49`, `:82-88` (the data layer's read: 10 s, no retries); `lovejoin.ts:2709-2711`, `:6814` (`split` reads non-quiet, classic pool included).
- **Claim:** every non-quiet pool read now waits for the Koios check.
  - The check uses Koios's backend: a 45 s timeout and retries (1 s and 3 s; one retry after a timeout), plus a 429's hold of up to 60 s.
  - That covers a return's or mix's build, a named pool, the status read and `madeBy`.
  - Before #336, `refresh()`'s only wait was the data layer's 10 s with no retry.
- **Scenario:** mainnet, data layer up, Koios slow, and someone launches a token pool that the data layer lists.
  - Any user who brings a private session back through Lovejoin, even classic-only, waits about 91 s before the build goes on: `tx_info` times out at 45 s, waits 1 s, then times out again. It's as long again if an `account_update_history` follows (rare).
  - It happens again at the next refresh (5 minutes) or the first read after the worker restarts, until Koios answers.
  - Scratch test: with Koios answering 503, one pool read waited 4,028 ms (three tries) and kept nothing new.
- **Fix:** don't hold the read on the check.
  - Either give the check a client that doesn't retry and has a short timeout, since a failed check only waits for the next list anyway;
  - or start the check without awaiting it, one in flight per network (as `scan()` does with `looking`), and let the next read take what it confirmed.
- **Test:** with Koios answering after N seconds, `serviceDeps(d).pools()` resolves within the data layer's bound, and a later read keeps the pool once Koios has answered.
- **Confidence:** high.

### F3 (low): on a device with no record yet, each pool read during a slow check asks the data layer and Koios again

- **Where:** `lovejoin-pools.ts:410-417` (the throttle's exception for a record without `listed`), `:432` (`this.answered.set(network, at)`), `:454`.
- **Claim:** the exception was written for Remove wallet: a record without `listed` means the next read asks again at once. It assumes `keep()` writes right after the data layer answers. `confirmed()` now sits in between.
  - On a fresh install, or after Remove wallet, there's no record while the check waits on Koios.
  - So every non-quiet pool read in that time deletes `answered`, asks `lovejoin/pools` again, and starts another Koios check with its own retries.
- **Scenario:** a fresh 1.7.0 install on mainnet (the bundled mainnet head start holds 0 pools), or right after Remove wallet; the data layer lists one token pool, and Koios is slow.
  - The user opens Lovejoin, and the check starts.
  - Then Refresh, a pool's page, or a running mix's `session-advance` (every 20 s) each send another `lovejoin/pools` and another `tx_info`. Each can take up to 91 s, and each holds its own pool read.
  - Scratch test: three pool reads sent three `lovejoin/pools` and three `tx_info`, where the throttle means one of each.
- **Fix:** allow one refresh in flight per network: a refresh that finds one running returns or awaits it, as `scan()` does. Or have `keep()` write `listed` before the check.
- **Test:** three concurrent `pools()` calls while Koios is held send one `lovejoin/pools` and one `tx_info`.
- **Confidence:** high.

### F4 (low, privacy): the device that started a pool is likely the first to ask Koios about it

- **Where:** `lovejoin-launch.ts:243-244` (the launch learns pools only through `discovery.look`/`known`); `lovejoin-pools.ts:565-584`; `docs/store/privacy-policy.md:28` ("the pools you started … stay on your device only, encrypted"), `:46`, `:93` ("naming nothing of yours").
- **Claim:** nothing tells discovery that this device built a launch, so a pool the user started is new to the device like any other. It's confirmed with Koios from the user's IP, usually first, since the starter is the one waiting to Bootstrap it.
  - The wallet seals "the pools you started", and the policy says the new request names nothing of yours.
  - Before #336, on mainnet with our server up, Koios heard nothing of a launch.
  - The same timing has existed on the Koios path (preprod, Koios-only, our server down) since 1.6.0.
- **Scenario:** on mainnet, a user starts a token pool from the private balance, so the chain ties it to no account.
  - About 200 slots later the data layer lists it.
  - The user's hub, open to Bootstrap the pool, reads pools, and `confirmed()` posts the launch's `tx_info` to `api.koios.rest` from their IP. That's minutes after the launch, likely before any other device reads it.
  - Koios can guess that this IP started the pool.
- **Fix (owner's call):** either skip Koios for a pool whose launch this wallet built and saw land, or add to the policy's *Starting a pool* sentence that Koios may tell from the first check's timing.
- **Confidence:** medium.

### F5 (low, tests): `confirmed()`'s trap rethrow has no test

- **Where:** `lovejoin-pools.ts:578-581`; `tests/wasm-review-fixes.test.ts`, whose Koios fake throws "not asked here", so `confirmed()` is never reached.
- **Claim:** mutation M5 (`catch (e) { standard = []; }`, traps swallowed) passes all 62 tests in `lovejoin-discovery` and `lovejoin-merged-review`. The only discovery trap test traps in `refresh()`'s `verified()`, before `confirmed()` runs.
- **Scenario:** a later edit drops the `isTrap` line. A trap in `lovejoinLaunchCheck` during the check is then taken for Koios down: the pool is left out, and the wallet carries on with a broken WebAssembly instance instead of locking (314-wasm#0, #330).
- **Test:** the index lists the fixture pool, `lovejoinVerifyPool` is the real one, `lovejoinLaunchCheck` throws `new WebAssembly.RuntimeError("unreachable")`, and Koios answers the launch. `refresh()` and `serviceDeps(...).pools()` both reject with that error.
- **Confidence:** high.

### F6 (low, docs): architecture.md and the module's comments still describe mainnet discovery before #336

- **Confidence:** high.
