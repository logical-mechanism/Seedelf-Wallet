## Findings

### 1. low (privacy/docs): the cheaper routes' "who sees what" leave out traffic the code sends on the private side's behalf

Each route promises that no single host ties the public account to the private side. Each misses a path the wallet already uses.

**Evidence:**
- **Split** (:344): "The public account's reads go to Koios, and the private side to the data layer and giveme.my, so neither operator alone ties the two."
  - One part carries every submit. `data-layer.ts:40` has `export type Part = "public" | "private" | "submit";`, and `:393–394` sends every `submitTx` to the data layer while `submit` is up.
  - Every send the wallet watches goes through that client (`pending.ts:476`, `submitWatched`), the public account's included. privacy.md:114 says what that tells the server: "**The public side and submits** tell it … the stake address, the transactions sent, from the IP address".
  - Each part falls back to Koios on its own. privacy.md:113: "Each part (the public routes, the private index, submits) goes to Koios on its own for 5 minutes when it can't answer". In code: `readFallback` (:117) and `submitFallback` (:136; 403, 413, 415, 429 and 503 go to Koios at once).
  - With the pool read from Koios, the wallet also asks Koios which boxes are its own: lovejoin.ts:5679 ("for those of `koios` … its tx_info") and :5702 (`koiosAlone()`).
- **Bring your own Tor** (:343): "a `chrome.proxy` PAC script that routes our hosts alone". Koios is one host for both sides, so a host-only PAC can't route its private-side requests apart. Those requests are the fallback windows above, everything under the Koios-only switch, and all of preprod (`networks.ts`: preprod has no `data` origin).
- **The shape** (:333): "the private side alone through Tor (submits, giveme.my, the private index's reads), the public account's reads direct, so no request ties the two". A private session's one-time account is read on the **public** part:
  - `sessions.ts:2390` calls `koios.credentialUtxos([keyHash])`;
  - in data-layer.ts, `credentialUtxos` (:244) and `addressUtxos` (:259) go through `read()` (:233), which uses `uses("public")`.

**Scenario:**
- The split is built as written. The data layer still receives the public account's sends, through the shared `submit` part, from the same IP address as the private submits and giveme.my. It ties the two exactly as it does today.
- Any 5-minute outage of the private part puts the private reads and submits at Koios beside the public reads, and the boxes too if the pool came from Koios.
- Under bring-your-own-Tor, the same windows send the private side to Koios directly from the user's IP. So does every private request on preprod or with Koios-only on.

**Fix:** one clause for each route.
- Split: "the public account's submits and status checks go to Koios too (the `submit` part split in two), and the private side's per-part fallback to Koios waits or is off, or the split holds only while the data layer answers".
- Bring your own Tor: "Koios can't be split by host: the private side's Koios fallback, Koios-only and preprod leave direct".
- The shape: "private sessions' one-time accounts too (read on the public part)".

Confidence: high.

### 2. low (docs): the one check said to be owed leaves out Koios, which the text relies on, and disagrees with the root README on giveme.my

**Evidence:**
- :346: "**Still unchecked: whether the data layer and giveme.my answer Tor exits today.** Every route above needs them to."
- Two of the PR's own claims need **Koios** to answer Tor exits:
  - :337: a gateway "would hide users from Koios (when the wallet falls back to it)";
  - :347: "past it the wallet reads Koios … so Tor users get slower, never banned".
- What the other docs say about Koios and Tor:
  - privacy.md:119: "whether it takes Tor exits is unchecked";
  - the root README, README.md:162, written by the owner (commit `8cba7a2f`, 2025-04-30): "`koios.rest` does not support Tor access".
- The same README line says "`giveme.my` does support Tor access".
- "Every route above" includes two that don't need Tor exits:
  - *Split who sees what* uses no Tor at all;
  - Nym's mixFetch exits through Nym's network, not Tor's.

**Scenario:**
- Whoever picks this up runs the dev-box check against the data layer and giveme.my only, finds both answer, and builds the DoS plan. Tor users who pass the shared bucket then fall back to a Koios that refuses them, as the README says it does. They are effectively banned, not slowed, and the private side's Koios fallback fails rather than hiding them.
- A reader also takes the split as gated on a Tor check it doesn't need.
- They run a check on giveme.my that the owner, who runs giveme.my and wrote that it supports Tor, can answer directly.

**Fix:**
- Make the line "whether the data layer, giveme.my **and Koios** answer Tor exits", noting the README's two statements: Koios no, giveme.my yes, both the owner's from 2025.
- Narrow "every route above" to "the Tor routes". For Nym, the question is its exits.

Confidence: high.

### 3. low (docs): bring-your-own-Tor's `proxy` permission can't be optional

**Evidence:**
- :343: "It needs the `proxy` permission (asked for at the switch, if Chrome lets it be optional)".
- Chrome doesn't allow it. `node_modules/@types/chrome/index.d.ts:9517–9530`, citing developer.chrome.com's permissions API as its source:
  `type ManifestOptionalPermission = Exclude<ManifestPermission, … | "geolocation" | "proxy" | …>`
- `chrome.proxy` also sets the profile's proxy configuration for all of Chrome, not just the extension's own requests (`@types/chrome`: "manage Chrome's proxy settings"). Only one extension can hold that setting at a time.
- The wallet's permissions today are `["storage", "alarms", "sidePanel", "scripting"]` (manifest.ts:84).
- The data layer was chosen partly because it needed "no install warning, and nothing disabled on update" (post-release-roadmap.md:290).

**Scenario:**
- The route is costed as an opt-in asked for at the switch. Built, it puts `proxy` among every install's required permissions. Its warning, as Chrome's permissions list gives it, is "Read and change all your data on all websites": recalled, not checked offline. So the update disables the wallet for every user until they accept, to serve only users who already run Tor.
- Its PAC script also replaces the user's own proxy settings, such as a system or enterprise proxy, for every host it doesn't route.
- The route fails for a user whose VPN extension already holds the proxy setting.

**Fix:** replace the hedge with the answer: "`proxy` can't be optional in Chrome, so it would be a required permission for every user, with a full-access warning and a disable on update, and its PAC script takes over the browser's proxy setting".

Confidence: high that it can't be optional; medium on the warning's wording.

### 4. nit (docs): "neither open nor an exit" sits beside "anyone can use it"

**Fix:** "open to anyone, though it reaches only Tor relays, and not an exit".

### 5. nit (docs): tor-js's HTTPS runs on an alpha crypto provider, a cost the list leaves out

**Evidence** (the clone at `8977093`):
- `crates/tor-js-wasm/Cargo.toml`: `rustls-rustcrypto = "0.0.2-alpha"` and `webpki-roots = "1.0.10"`;
- `src/runtime.rs:8`: "TLS: Uses rustls with rustls-rustcrypto (pure-Rust crypto for WASM)";
- `src/lib.rs:445`: "the Mozilla CA bundle (compiled in via webpki-roots)".

**Scenario:** with tor-js, the private side's TLS to the data layer and giveme.my leaves Chrome's TLS stack for an alpha, unaudited provider, with root certificates frozen at each release. *And in the extension* (:341) lists the offscreen document and the 1.9 MB, not this. The owner wants to "approach this the right way", and a pick-up would weigh it.

**Fix:** one more clause under *And in the extension*.
