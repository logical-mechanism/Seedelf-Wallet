# PR #331: *Web Wallet required*, a job that always reports (label `pr331`)

Merge `3b32b92e` (head `c5d19d3f`, base `4610555a`). Reviewed on HEAD `6bca8bec`. Nothing in `.github/` changed after it (`git log babb8e76..6bca8bec -- .github/` is `c5d19d3f` alone).

## Verdict

**The YAML does what it says, and it fails closed in every failure I could build.** The workflow-level path filter is gone. `changes` lists the PR's files from the API, `check` (unchanged) runs only when that list touches `seedelf-platform/` or the workflow, and `required` (*Web Wallet required*, `if: always()`) is green only when `check` passed, or was skipped with `platform=false`. The following all turn it red:

- an API error mid-pagination;
- `changes` failed or cancelled;
- `check` failed, cancelled, or skipped while `platform=true`.

A re-run of `required` alone gives the same answer. The full path ran correctly on GitHub for #331 and #333–#338.

**The problem is outside the YAML: the protection the PR tells the owner to turn on can't stop what it's for (F1, medium).**

- `main`'s classic protection requires one approving review, with `enforce_admins` off. Every PR from #323 to #338 merged with zero reviews, so every merge goes through the admin bypass, and that bypass skips required status checks too.
- In this very range, 12 of the 13 PRs that had a Web Wallet check merged before the check finished, 9 to 58 minutes early. #338 merged at 22:55:43Z, and its check finished at 23:28:25Z.
- Requiring *Web Wallet required* as instructed (Settings → Branches → main → *Require status checks to pass*) changes nothing about that path.

**Smaller holes, where a PR that changes `seedelf-platform/` gets a green *Web Wallet required* without the check:**

- F2: a rename out of the folder. The API's `filename` is the new path, and `previous_filename` is ignored.
- F3: a base change. `edited` isn't among the default types, so nothing re-runs.
- F5: a PR of over 3,000 files.
- F7: a PR that rewrites the gate itself.

**Also:**

- F4: `check` and the new `required` run with a write-all `GITHUB_TOKEN` persisted in `.git`, while `check` runs every dependency's scripts. This predates the PR; data-layer.yml already fixed it.
- F6: the docs say the protection requires the job; it requires nothing yet.
- F8 (owner's call): data-layer.yml has the never-reporting shape #331 removed, and its job name collides with a `check` that now reports *skipped* on every PR outside `seedelf-platform/`.

**For the release:** #338's run is the only CI run of HEAD's exact tree, and it's green on every step.

- `62be5bc4^{tree}` = `6bca8bec^{tree}` = `8bd149a8`, because #338's head sits directly on #337's merge.
- Its `check` job finished green at 23:28:25Z, the store package and its e2e included, and *Web Wallet required* was green at 23:28:29Z. The section [The one CI run of HEAD's tree](#the-one-ci-run-of-heads-tree) has each step.

   - success / true / success;

5. **Forks, re-runs, concurrency, `needs`.**
   - A fork's token is read-only. That covers `pull-requests: read`, and the repository is public. A first-time contributor's run waits for approval, so the check stays pending, which fails closed.
   - Re-running `required` alone reuses its `needs`' results. Re-running the whole run re-tests the original event's merge commit (`GITHUB_SHA` doesn't change), while `changes` reads the PR's current files.
   - There's no `concurrency` group: a superseded run reports to its own head only.
   - When `changes` fails, `check` is skipped by the implicit `success()`, `PLATFORM` is empty, and `required` exits on `CHANGES` first.
   - A `[skip ci]` head or a broken workflow file means no run at all, so the check stays pending. That fails closed.

   - the only mentions of `seedelf-contracts`, `seedelf-data` and `.github` there are comments.

## Findings

### F1 (medium, ci, high confidence): the required check the PR asks for is skipped by the owner's own merge path

- **Files:** `.github/workflows/web-wallet.yml:135-155`, `seedelf-platform/seedelf-web-wallet/docs/development.md:13`, `seedelf-platform/seedelf-web-wallet/docs/post-release-roadmap.md:36`.
- **Claim:** the PR's stated goal ("Requiring the check on `main` stops that from happening again") needs a rule the owner's merges obey. `main`'s classic protection has `enforce_admins: false` and requires one approving review. A self-authored PR can never meet that, so every merge in the range used the admin bypass. GitHub says "by default, the restrictions of a branch protection rule don't apply to people with admin permissions to the repository", and that bypass covers status checks as well.
- **The owner's step as written adds *Web Wallet required* to the rules already bypassed on every merge.** Strict mode (*Require branches to be up to date*) has had nothing to apply to while no check is required, and PRs merged out of date: #331's head lacked #332's merge, and #337's lacked #336's.
- **Scenario:**
  1. The owner requires *Web Wallet required* as told.
  2. A 1.7.x fix PR opens, and its check runs for about an hour.
  3. The merge box says *Merging is blocked* (no approving review, check pending) and offers the admin's bypass checkbox. That's the box the owner ticks on every PR today.
  4. Ticked, the PR merges at once. The check fails 40 minutes later.
  5. `main` is red, and nothing runs on `main` to show it (development.md:15).

  That is #323 again: a broken private Bootstrap merged onto the release line.
- **Evidence:**
  - Branch protection: `{"strict":true,"contexts":[],"checks":[]}`, `"required_approving_review_count":1`, `"enforce_admins":{"enabled":false}`.
  - `gh api …/pulls/<n>/reviews` returns `[]` for #323, #324 and #330–#338, all `merged_by` logicalmechanism.
  - Merge time against the end of the Web Wallet `check` on the PR's head:

    | PR | Merged (UTC) | Check finished (UTC) |
    |---|---|---|
    | #325 | 17:36:00 | 17:16:55 (the only one that waited) |
    | #326 | 17:36:12 | 18:10:20 |
    | #328 | 18:11:17 | 18:47:05 |
    | #329 | 15:49:28 | 16:42:21 |
    | #330 | 16:22:22 | 16:58:35 |
    | #331 | 16:26:02 | 17:21:57 (its own *Web Wallet required* reported at 17:22:03) |
    | #332 | 16:25:43 | 17:23:49 |
    | #333 | 17:14:44 | 17:27:32 |
    | #334 | 17:13:35 | 17:42:09 |
    | #335 | 17:14:00 | 18:02:53 |
    | #336 | 18:30:13 | 18:39:08 |
    | #337 | 18:30:28 | 19:14:32 |
    | #338 | 22:55:43 | 23:28:25 |
- **Fix:** make the owner's step one their own merges can't skip, and word roadmap item 2 and development.md:13 to match. Either:
  - **(a)** Settings → Branches → main: required approvals 0, tick *Do not allow bypassing the above settings*, and keep *Web Wallet required* and *up to date*. Optionally allow auto-merge, so that *Enable auto-merge* lands a PR the moment its check is green.
  - **(b)** Keep the classic rule, and add a branch ruleset on `main` that requires *Web Wallet required* with an empty bypass list.

  Either way the cost is the owner's to accept: with *up to date* enforced, each PR re-runs its ~1 h check after every other merge. That is also what makes `main`'s tree tested as one, which this range's never was.
- **If the owner keeps merging by bypass:** the honest alternative is a run on `main` after each merge (`push: branches: [main]`, with `changes` treating a push as `platform=true`). That's the owner's call.
- **Test:** after the owner's step, put a comment-only change under `seedelf-platform/` in a PR. While its check runs, the merge box must offer no bypass and no enabled merge button. Today it offers the bypass.

### F2 (low, ci, high confidence): a rename out of `seedelf-platform/` skips the check and goes green

- **Files:** `.github/workflows/web-wallet.yml:27-28`, `docs/development.md:13`.
- **Claim:** `changes` reads `.[].filename`, and for a rename that's the new path; `previous_filename`, the old one, is ignored. A PR that moves a file out of `seedelf-platform/` therefore gets `platform=false`, the check skipped and a green *Web Wallet required*, although it removed a file the check builds or reads.
- **Scenario:** a PR moves the shared fixture `seedelf-platform/seedelf-core/tests/fixtures/lovejoin-pool-vectors.json` to a root `fixtures/` folder and updates seedelf-data's `include_str!`.
  - The API answers `{filename: "fixtures/lovejoin-pool-vectors.json", previous_filename: "seedelf-platform/seedelf-core/tests/fixtures/lovejoin-pool-vectors.json", status: "renamed"}`, plus the seedelf-data file.
  - The grep finds no `seedelf-platform/` path, so `check` is skipped and the PR is green.
  - Core's vectors test and `extension/tests/lovejoin-planner.test.ts:503`, which `readFileSync`s that path, now fail on `main`.

  Renaming `web-wallet.yml` itself also gives `platform=false`.
- **Evidence:**
  - `web-wallet.yml:27`: `files=$(gh api --paginate "$FILES" --jq '.[].filename')`.
  - PR #329's own answer shows the shape: `{"filename":"…/docs/archive/plans/chunk-34-token-pools.md","previous_filename":"…/docs/plans/chunk-34-token-pools.md","status":"renamed"}`.
  - The verbatim step against that shape gives `platform=false`. A deletion, where `filename` is the old path, gives `true`.
  - GitHub's docs don't say how the old path filter treated renames, so this isn't claimed as a regression. getsentry's action-filter-paths turns rename detection off for exactly this reason.
  - The repository's history has no rename out of `seedelf-platform/` (`git log --diff-filter=R`), so the likelihood is low.
- **Fix:** `--jq '.[] | .filename, (.previous_filename // empty)'`.
- **Test:** the verbatim step with a fake `gh` answering a rename out of the folder should give `platform=true`. It gives `false` today.

### F3 (low, ci, high confidence on the mechanism, low likelihood here): a base change doesn't re-run, and a stale green stands

- **Files:** `.github/workflows/web-wallet.yml:9-10`, `docs/development.md:13`.
- **Claim:** `on: pull_request:` with no `types` runs only on opened, synchronize and reopened. Changing a PR's base fires `edited`, so nothing re-runs. The green computed against the old base stays on the head commit, which is what branch protection reads, although the PR's files, and so whether the check must run, depend on the base.
- **Scenario:**
  1. `web-wallet/b` is cut from `web-wallet/a`, which carries a `seedelf-platform/` change and was cut from `main`'s head.
  2. PR b→a adds only a root `CLAUDE.md` line. Its files are `[CLAUDE.md]`, so the check is skipped and the PR is green.
  3. The owner retargets the PR to `main`. Its files now include a's change, but no run happens.
  4. b is already up to date with `main`, so even an enforced strict rule passes, and a's change merges unchecked.

  A re-run doesn't help: it re-tests the original merge commit.
- **Evidence:**
  - `web-wallet.yml:9-10`: `on:` / `pull_request:`.
  - GitHub: "By default, a workflow only runs when a pull_request event's activity type is opened, synchronize, or reopened."
  - No PR since #266 has targeted anything but `main`, hence the low likelihood.
- **Fix:** the smallest is a line in *Branching*: "after changing a PR's base, close and reopen it (or push) so its check runs against the new base." Or add `edited` to the types and let the whole workflow re-run on every edit, which is costly: each body edit re-runs the hour-long check.

  Never gate `required` with an `if` that can skip it. GitHub says "Required status checks must have a successful, skipped, or neutral status", so a skipped required check counts as passing.

### F4 (low, security/ci, high confidence; predates the PR): a write-all token persisted in `.git` while `check` runs every dependency's scripts

- **Files:** `.github/workflows/web-wallet.yml:9-12`, `:42`, `:85-87`.
- **Claim:** the workflow sets no top-level `permissions`, and the repository's default is `write`. So `check`, and since #331 `required` as well, get a write-all `GITHUB_TOKEN`.
  - `actions/checkout@v4` persists that token in `.git`.
  - `check` then runs every npm lifecycle script (`npm ci`), every crate's build script, and `dtolnay/rust-toolchain@master`, which is a moving ref.
  - data-layer.yml drops both for this reason ("No token left in .git: the build runs every dependency's build script"). #331 scoped only `changes` down.
- **Scenario:** a compromised dependency arrives in a lockfile-bump PR from a same-repo branch. Its install script reads the persisted token, and with `Statuses: write` posts a success named *Web Wallet required* on the head. It could equally push to a branch, or edit PRs and issues.
- **Evidence:**
  - Job 122947931189's log: "GITHUB_TOKEN Permissions: Actions: write … Checks: write … Contents: write … PullRequests: write … Statuses: write". `required`'s job 122981073437 shows the same.
  - `gh api …/actions/permissions/workflow` gives `{"default_workflow_permissions":"write"}`.
  - data-layer.yml:24-25 and :34-37 do the hardening.
- **Fix:**
  - A top-level `permissions: { contents: read }`. `changes`' own `pull-requests: read` still replaces it there.
  - `with: persist-credentials: false` on `check`'s checkout.

  Nothing in `check` uses the token: rust-cache and setup-node's cache use the Actions runtime token.

### F5 (nit, ci, medium confidence): a PR of over 3,000 files can skip the check silently

- **Files:** `.github/workflows/web-wallet.yml:27`.
- **Claim:** "Responses include a maximum of 3000 files", and they come back in path order. `seedelf-platform/` sorts after `.github/`, the root files, `seedelf-contracts/` and `seedelf-data/`.
- **Scenario:** a PR vendors seedelf-data's crates (`cargo vendor` into `seedelf-data/vendor/`, thousands of files) and changes one line in seedelf-core. The first 3,000 entries are all vendor files, so the check is skipped and the PR is green.
- **Evidence:**
  - GitHub's REST docs, *List pull requests files*.
  - #329's answer came back in path order.
  - `git ls-files`: 137 tracked files sort before `seedelf-platform/`.
  - The old path filter had the same 3,000 limit, so this isn't a regression.
- **Fix:** fail safe. Pass `github.event.pull_request.changed_files` as `CHANGED`, and set `platform=true` when `wc -l <<<"$files"` is less than `CHANGED`. Adding `?per_page=100` also cuts a 3,000-file lookup from 100 calls to 30.

### F6 (nit, docs, high confidence): the docs say `main` requires the job; it requires nothing yet

- **Files:** `docs/development.md:13`, `.github/workflows/web-wallet.yml:135-136`.
- **Claim:** "That job is the one `main`'s branch protection requires" and "The one check main requires (its branch protection names *Web Wallet required*…)" are both untrue until the owner's step (roadmap:36, "left, the owner's: requiring it").
- **Scenario:** a session reading *Branching* trusts that a green `main` is a checked `main`, or that a PR can't merge mid-check.
- **Evidence:** `required_status_checks.contexts []` and `checks []`.
- **Fix:** "is the one … is to require (roadmap item 2)" until the owner does it, worded together with F1.

### F7 (nit, ci, high confidence): a PR that edits `web-wallet.yml` decides its own *Web Wallet required*

- **Files:** `.github/workflows/web-wallet.yml:140-155`.
- **Claim:** a `pull_request` run uses the workflow from the PR's own merge commit. A PR, a fork's included, can rewrite `required` to `exit 0`, and its required check goes green whatever `check` says. This is inherent to GitHub, and the owner merges by hand, so it's a reading rule.
- **Scenario:** a fork PR changes seedelf-core and sets `required`'s script to `exit 0`. `check` fails, *Web Wallet required* is green, and under an enforced rule the PR is mergeable.
- **Fix:** a line in *Branching*: "a PR that touches `.github/workflows/` decides its own required check: read that diff before trusting it."

### F8 (owner-call, ci, high confidence on the shape, medium on how GitHub breaks the name tie): data-layer.yml keeps the never-reporting shape

- **Files:** `.github/workflows/data-layer.yml:5-22`, `:28`, `.github/workflows/web-wallet.yml:34`.
- **Claim:** data-layer.yml has the workflow-level path filter #331 removed. If its `check` is ever required, every PR outside its paths waits for good: "checks associated with that workflow will remain in a Pending state". That's harmless today, since nothing is required.

  Its name `check` now has a twin: since #331, web-wallet.yml's `check` reports *skipped* on every PR that doesn't touch `seedelf-platform/`, every data-layer-only PR included, and a skipped required check counts as passing.
- **Scenario:** to keep `main` deployable, the owner requires `check`.
  - A wallet-only PR waits for ever on the data layer's check, which never runs.
  - A data-layer-only PR carries two `check` runs: the data layer's (red) and the wallet's (skipped, which counts as passing).
- **Fix, if the owner ever wants the data layer gated:** the same three-job shape with its own name (*Data layer required*), and a distinct `name:` on web-wallet's `check`.
