# PR #330: a trap under a run a page's request doesn't wait for (label `pr330`)

Merge `81397dc4` (commit `0154d55e`). Reviewed on HEAD `6bca8bec`.

## Verdict

**#330 does what it says, and it's right.** `unawaited(ctx, run)` (handlers.ts:48-52) locks the wallet on a trap under each of the three runs and drops any other failure exactly as `.catch(() => undefined)` did. It adds no lock loop. Its tests fail without it. The docs match the code.

Two low findings, neither caused by #330:

1. **Nothing pins site 1's other half.** #330's restore test mocks `sessions.scan`. No test checks that the real scan hands a trap from its own WebAssembly calls on to its promise. If the scan's catches swallowed traps, 63 tests would stay green and a real restore would again leave the wallet unlocked on a broken instance.
2. **A trap swallowed inside the wallet's queue.** In tx-view.ts, `ownRegister`'s bare `catch {}` (lines 216-220) runs inside `withKeys`, so `serial` never sees a trap from `keys.seedelf.isOwned`. The wallet stays unlocked, and Transaction details mark the user's own output as someone else's. This is pre-existing (8de4dc64, before 1.6.0) and in the same class as #330. No trigger is known.

## The brief's questions

### `isTrap` (wasm.ts:46-50)

It counts three kinds of error as a trap:

- **Any `WebAssembly.RuntimeError`.** That covers `unreachable`, which is every Rust panic, including #332's new overflow panics in core, crypto and koios. It also covers memory out of bounds and an allocation failure (abort).
- **A `RangeError` with a WebAssembly frame on its stack.** This is 1.6.0's 314-wasm#0, a stack overflow inside WebAssembly.
- **An `Error` carrying one of wasm-bindgen's borrow messages.**

It does not count:

- a JavaScript `RangeError` with no WebAssembly frame;
- `JsError` refusals;
- "null pointer passed to rust";
- the glue's "Invalid stale object from previous Wasm instance";
- a load failure, which `loadWasm` turns into a translated `Error`.

### `wallet.trapped()` (wallet.ts:569-571 → `broken` 598-609)

- **What it does.** It is serialised in the wallet's queue. It sets `lockedBy = "trap"`, then `wipe()`s: it clears session storage but `SESSION_SENDS` and `SESSION_DAPP_REFUSED`, stops the auto-lock alarm and drops the keys. Then it calls `fresh()`: `freshWasm` resets in place, or, without the reset function, calls `chrome.runtime.reload()`. Last comes `changed()`: `STATE_CHANGED`, `dapp.stateChanged`, and `runSessions(unlock)`, which finds the wallet locked and stops the sessions alarm (runs.ts:51-53).
- **It is not idempotent.** Every call repeats all of that, whether the wallet was unlocked, locked or absent.
- **Being called twice is harmless in practice.** Every caller (`answerUi`, runs.ts, `unawaited`) calls it in the same microtask checkpoint as the rejection that carries the trap. Some promises are shared:
  - the pump's per-network promise is shared by the alarm's run and Home's poll (parts.ts:494-531);
  - the scan's promise is shared with Find leftovers (sessions.ts:2562-2563).

  Two calls therefore queue back to back, before any unlock message can arrive. Objects made on the first fresh instance turn stale after the second reset. The glue then throws a plain `Error` that `isTrap` doesn't count, so the reset can't cascade into another lock.
- **A trap that lands after a user's lock** sets `lockedBy` to `"trap"`, as under `answerUi` and runs.ts. The Unlock screen then says WebAssembly stopped working, which is true.
- **A small wording slip in the PR body.** It gives "the poll's own request and its pump" as its example of two calls. The poll's own request (`pending.pending`) makes no WebAssembly call. The real pairs are the alarm's run with the poll's pump, and the restore's scan with Find leftovers. The claim itself ("does no harm") holds.

  - #336's `confirmed()`.

### Can a trap there now loop?

Not because of #330:

- **The pump.** A lock wipes session storage, and with it what waits (`seedelf.waiting.<network>`, `seedelf.waitingPart.*`). After an unlock the poll's pump has nothing to send. It can't trap outside the queue anyway.
- **The scan.** It runs once per restore. Find leftovers is an awaited page request, so `answerUi` already locked on its trap.
- **Bring every box back now.** `bringing` is sealed in local storage and survives the lock. The unlock's run goes on with it: lovejoin.ts:6170-6172 has no unlock check, by design ("from the unlock's run on"). A trap that recurred on every run would re-lock at every unlock through runs.ts, with or without #330, and a trap never counts toward `BRING_FAILED_RUNS` (lovejoin.ts:6588-6591, 6745-6748). #330 only makes the first lock immediate rather than at the alarm's next minute. No recurring trigger is known: core's `Asset::add` is checked, and lovelace sums can't reach `u64::MAX`.

### Is a non-trap failure handled as before?

Yes. It is swallowed exactly as before (handlers.ts:49-51), and M2 shows the tests hold that.

**Where:** handlers.test.ts:128-136 mocks `sessions.scan`; sessions.ts:2727-2742 and 3863-3866 are the catches the real scan relies on.

**Scenario:** someone later changes `hexOf`, `read` or `liveOrders` in sessions.ts to `return undefined` on any error, as the old code did. Every test stays green. M4 shows it: restore-scan.test.ts and handlers.test.ts, 63 tests, all pass.

Site 3 is pinned end to end (run-traps-review-fixes.test.ts:261, :277). Site 2 has no WebAssembly outside the queue.

**Fix:** add a test of the real scan, as in my scratch tests:

- **A:** in restore-scan.test.ts, `signing(t, { wasm: { ...loadTestWasm(), cip30Address: () => { throw new WebAssembly.RuntimeError("unreachable"); } } })`, with `usedWith` and `swapped` as in "finds an order still open…", then expect `sessions.scan("preprod")` to reject with a `WebAssembly.RuntimeError`.
- **B:** through `handle({ type: "restore-wallet", … })` on a fresh `testBalances()`, with session 0's stake marked used. Derive it from the phrase with `OneTimeAccounts.fromEntropy(phraseToEntropy(phrase)).rewardAddress(Network.Preprod, 0)`. Then `vi.waitFor` the status `{ state: "locked", lockedBy: "trap" }`.

Both pass on HEAD. Both fail under M4, and B fails under M3.

### 2. (low, correctness) `ownRegister` swallows a trap inside the wallet's queue

**Where:** tx-view.ts:214-224.

```ts
function ownRegister(wasm: typeof Wasm, keys: Keys, register: TxRegister): boolean {
  const r = new wasm.Register(register.generator, register.publicValue);
  try {
    return keys.seedelf.isOwned(r);
  } catch {
    // Points that don't decode, or aren't in the prime-order subgroup, can't be anyone's to spend.
    return false;
```

**Why `serial` never sees the trap:** `markYours` calls it inside `wallet.withKeys` (tx-view.ts:239, 247). The catch returns `false`, so `serial`'s guard (wallet.ts:577-590) never sees the trap. Lines 184-186 show the intent to hand one on (`markYours(...).catch((e) => { if (isTrap(e)) throw e; })`), but the inner catch drops it first.

**Scenario:** the user opens Transaction details on a private payment's review, or a site's prompt shows its transaction. `keys.seedelf.isOwned` traps.

- The details answer with the user's own change marked as someone else's.
- The wallet stays unlocked on the broken instance (`lockedBy` undefined) until something else traps.
- Shown in the copy: the outputs came back as `theirs,theirs`; the state was `unlocked`, with `lockReason` undefined.

This is pre-existing (8de4dc64, 2026-10-05), outside #330's three, and of the same class as #330 and 1.6.0's L3. `isOwned` runs only on points `decodeTx` already found payable, so no trigger is known.

**Fix:**

```ts
catch (e) {
  if (isTrap(e)) throw e;
  return false;
}
```

`serial` then locks (`lockedBy: "trap"`). The details still answer, without that output's mark (line 184's catch takes the `WalletLocked`), and the page follows the lock. M5 checked this.

**Test:** build a private payment as tx-view.test.ts:113 does. `vi.spyOn(wasm.SeedelfKey.prototype, "isOwned")` to throw `new WebAssembly.RuntimeError("unreachable")`. Call `txView`, then expect `wallet.state()` to be `"locked"` and `lockReason()` to be `"trap"`. It fails on HEAD and passes with the fix.
