**Who and how:** a stranger re-randomizes a user's register, which sits on chain beside each Seedelf, and pays the contract three outputs of 2^63 − 1 of one token. That costs about 5 ₳, and the ADA becomes the user's. `is_owned` accepts each row. `collect_all_wallet_utxos` takes every owned row that holds no Seedelf, with no cap. Its only caller is `balance`, so `balance` is the CLI's only listing of a user's private UTxOs and their total.

**`balance`:** `balance.rs:39`'s `assets_of` overflows its checked add. `balance` prints the Seedelfs, then "Error: Can't Merge Assets: Can't Merge Assets: Can't Add Asset To Assets: Asset addition overflow", on every run. It never prints the UTxO list, the balance or the tokens.

**`sweep --all`:** it hands `sweep_all` the first 20 owned rows unfitted. `ScriptSpend::new` takes them as given, and `draft()` then fails at `remainder`'s `assets_of` before any network call.

**What still works:** `transfer`, `sweep -l` and `util mint` go through `select_script_inputs`, which fits rows first (`build.rs:2556`), so they still pay. No money is lost or stuck.

**Two corrections to the finding:**
1. With 2^63 − 1 per row, two rows total 2^64 − 2, which fits a u64. So `sweep --all` fails only when all three are among its 20, not "whenever two" are. A stranger who sends 2^63 or more per row (an output may hold up to 2^64 − 1) makes any two enough.
2. "Until a code change" is slightly too wide. Pushing one junk row out of the contract with `sweep --utxo … --asset …` clears `balance`. But the error names no row or token, and `balance` never lists them, so the user can only find them from outside the CLI.

//! Chunk 51, finding r4#2: a stranger pays the contract three UTxOs of
//! 2^63 − 1 of one junk token, each under a fresh re-randomization of the
//! user's register (the register sits on chain beside every Seedelf). The
//! user's key owns all three, so every scan of the user's UTxOs takes them.

use seedelf_cli::commands::sweep::{SweepArgs, run};
use seedelf_core::utxos;

#[tokio::test]
async fn sweep_all_still_goes_when_a_stranger_pays_the_users_register_tokens_past_a_u64() {
    let mut scenario = Scenario::start().await;

    // The user's own: 100 ₳, and 5 ₳ with 1,000 tokens bought.
    let bought = ("bb".repeat(28), hex::encode("BOUGHT"), 1_000);

    let mut rows = vec![

        wallet_utxo(scenario.scalar, 2, 5_000_000, std::slice::from_ref(&bought)),
    ];

        (3..=5).map(|n| wallet_utxo(scenario.scalar, n, 1_500_000, std::slice::from_ref(&junk))),
    );

        .expect("the scan");

    );

    scenario.mount_evaluate(5).await;

            address: Some(external_address_bech32()),
            lovelace: None,
            all: true,
            assets: vec![],
            ada_handle: None,
            utxos: None,

        PREPROD,
        VARIANT,
    )

    let tx = decode_tx(&scenario.submitted_cbor().await);
    assert_sound_transaction(&tx, &scenario, &params);
    assert!(
        tx.inputs.contains(&(tx_hash(1), 0)),

        "the user's bought tokens should be swept"
    );

        "sweep --all sends everything it spends to the address"
    );

## Impact: partly, low

The mechanism is real and a stranger can trigger it. Three junk rows of 2^63 − 1 under re-randomizations of the user's register cost about 5 ₳, most of which lands in the victim's balance. After that, `seedelf-cli balance` errors on every run before it prints the UTxO list or any total. There's no import path into the web wallet, so that is the CLI user's only view of the private balance.

The harm is narrower than medium:
- Nothing is lost, locked, misdirected or overpaid. Every paying command fits its rows first: `transfer`, `sweep -l`, `sweep --asset` and `util mint` all go through `select_script_inputs`, which calls `fitting`. All the ADA and every token the user can name still pays.
- No wrong figure is shown: the command errors, and an error is less harmful than a false number.
- `sweep --all` breaks only while all three junk rows are among its 20. Two rows of 2^63 − 1 sum to 2^64 − 2, which fits a u64. Its documented alternative, `sweep -l`, works.
- "Until a code change" holds only for a harder variant. For the stated shape, one `sweep --asset <junk>=9223372036854775807` restores `balance`. The token's unit has to come from outside the CLI: `util history` lists the receive transactions, and an explorer shows the token.
- If each junk row also carries a reference script, the CLI's selection never picks it. Then only `--utxo`, with outpoints found on an explorer, or a CLI release clears it. Even then the user's own money keeps moving.

So the user loses a read-only view and a convenience command, and their funds keep moving: low, not "a stuck state with no way out". I was unsure between low and medium, so I took the lower grade. It's outside SECURITY.md's bounty (no loss of funds).

**Evidence:**

The mechanism holds:
- balance.rs:34-37 takes every owned row through `collect_all_wallet_utxos` (utxos.rs:32-53). That function has no cap, no `fitting` and no `eval::refusal` filter, and any re-randomization of the user's register passes `is_owned` (utxos.rs:44).
- balance.rs:39 then calls `assets_of`. The chain is utxos.rs:342 → assets.rs:316 → assets.rs:68-69 (`checked_add`, "Asset addition overflow").
- The UTxO list and the totals print only after that (balance.rs:41-64). The Seedelfs still print, at :21-32.
- lib.rs:83-84 prints "Error: Can't Merge Assets: Can't Merge Assets: Can't Add Asset To Assets: Asset addition overflow". It names no token and no outpoint.

The `sweep --all` path:
- sweep.rs:150-158 takes `collect_wallet_utxos`, the first 20 owned rows (utxos.rs:111-137).
- `build::sweep_all` (build.rs:3538) hands them to `ScriptSpend::new` as given.
- The remainder then fails at build.rs:2093, `assets_of(spent)`.
- It's narrower than the finder says: 2 × (2^63 − 1) = 2^64 − 2 ≤ u64::MAX, so all three junk rows must be among the 20. Any two would do only if each junk row holds 2^64 − 1. A wallet with 20 or fewer owned rows always includes all three.

The paying paths fit their rows:
- `transfer` goes transfer.rs:124 → `build::transfer` (build.rs:3120) → `select_script_inputs` (build.rs:2535). Its `fitting` call at :2556 leaves out the row that would overflow.
- `sweep -l` and `--asset` go build.rs:3381 → `sweep_many_apart` → the same selection.
- `util mint` goes through `mint_apart` → `select_script_inputs`.
- `remove` spends only the Seedelf's UTxO.

The way out:
- `sweep --asset junk=9223372036854775807` reaches `holding` (build.rs:2949-2979), which takes one of the junk rows that fit. The two left sum to 2^64 − 2, and `balance` totals again.
- The unit can come from util/history.rs:34-35, which lists receive transactions at the enterprise form only, plus an explorer.
- The hardened variant: a junk row with a reference script is never picked (eval.rs:62-69, build.rs:2553), but `balance` still counts it.

The cost to the stranger:
- One transaction mints at most 2^63 − 1 of an asset, so this takes three mints.
- It also takes three contract outputs at about 1.55 ₳ minimum ADA each, for an output of roughly 200 bytes with a register datum.
- In all, about 5 ₳, and the stranger gains nothing.
