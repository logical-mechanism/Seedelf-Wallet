## Trace: confirmed, high

The finding holds as described. `seedelf-cli external sweep` hands every row at the external (dApp) address to `build::external_sweep`. That function's first step adds up every row's tokens with a checked u64 add. So three UTxOs from a stranger, each holding 2^63 − 1 of one junk token (about 4–5 ₳ of minimum ADA, which the ledger accepts), make every run fail with "Error: Can't Merge Assets". Only the address's key can spend the junk, and the only CLI command that signs with that key is this all-or-nothing sweep, which takes no arguments. So the user's ADA and tokens there can't leave through any tool Seedelf ships. Recovery needs custom code: `util expose-key` prints only the BLS scalar, and the web wallet has no import path for CLI wallets. `external balance` fails the same way right after it prints the address. Every CLI external address carries the same stake credential, so a stranger can list them all. I found no guard, no earlier check and no covering test. The web wallet is not affected: its session return builds only from `plan_return`'s fitted rows. The launch review's H6 fix (f446cb27) never touched this path. The code is identical at the latest CLI tag, 0.7.0, which SECURITY.md puts in scope, and the bug is recorded nowhere. Severity is high on the brief's scale: a stranger strands funds, and the project graded the same shape high for the web wallet's session return (H6). The finder's two other ways in, a sweep over 16 KiB or over 200 KiB of reference scripts, hold on reading but cost the stranger hundreds of ₳, and I didn't test them. One citation is wrong: MAINNET_STAKE_HASH is at constants.rs:76, not :145. It changes nothing.

//! Chunk 51, finding r4#1: a stranger's three UTxOs of 2^63 − 1 of one junk
//! token at the CLI's external wallet (its dApp address, a plain key address
//! anyone can pay) must not stop `external sweep` from bringing the user's own

//! 2^64 − 1 of a token in an output, so a stranger can send these for about

async fn external_sweep_still_goes_when_a_stranger_sends_tokens_past_a_u64() {
    let mut scenario = Scenario::start().await;
    let dapp = dapp_address_for(scenario.scalar)
        .to_bech32()
        .expect("dapp bech32");

    // The user's DEX proceeds: 300 ₳, and 5 ₳ with the 1,000 tokens bought.
    let bought = ("bb".repeat(28), hex::encode("BOUGHT"), 1_000);

## Impact: confirmed, high

The impact holds at high. I tried to refute it on reach, cost, loss and ways out, and none of them lowers it.

1. **Reach.** Every CLI user's external address on mainnet has the [LOGIC] pool's stake key as its staking part (address.rs:154, constants.rs:76). Anyone can list them all from that one stake credential. The README's flow also makes each one a public address that DEX proceeds are sent to.
2. **Cost.** A mint is capped at 2^63−1 per transaction, but an output can hold up to 2^64−1. So two outputs are enough: 2^64−2 and 2, or 2^64−1 and 1. That is about 2.4 ₳ of minimum ADA, which lands at the victim's address and is stuck with the rest, plus about 0.5 ₳ in mint fees that can be shared across victims. The total is about 3 ₳ a victim, a little under the finder's 3.5–5 ₳.
3. **Effect.** `assets_of` errors at build.rs:564, before anything is built, and every rerun fails the same way. `external balance` prints the address, then fails before it shows any count or total. The user sees only "Error: Can't Merge Assets".
4. **No way out in the product:**
   - no other CLI command signs with the external key;
   - `Sweep` takes no arguments, so there is no coin control;
   - the web wallet can't import a CLI scalar;
   - CLIs before 0.5.0 wrapped the sum into a transaction the ledger refuses, and those up to 0.4.10 can't spend at all;
   - a restore gives the same address, and waiting changes nothing.
5. **Not lost or taken.** The key holder can still move the funds with custom code: `util expose-key` prints the scalar, the ed25519 seed is the ed25519 public key of that scalar, and cardano-cli can then sign a hand-built transaction. A CLI patch would also free them.
6. **Precedent.** Launch review H6 had the same ways out (session keys at 24301', "an address no other wallet reads"). It was graded High and fixed before launch. This is the CLI path its fix (f446cb27) never touched.
7. **The owner's rule supports it.** The ledger accepts a sweep of the rows that fit. It would even accept all of them, with the token split over two outputs.
8. **In scope.** The code is CLI 0.7.0, the latest CLI tag, so it is in SECURITY.md's bounty scope.

**Where the finding overstates:**
- "Forever" means until a CLI patch or custom code.
- The attacker gains nothing: it is griefing.
- The size form (over 16 KiB) and the reference-script form (over 200 KiB) cost tens to hundreds of ₳, nearly all of it landing at the victim's address.

None of this changes the brief's category for high: a stranger can strand funds.

How many users it reaches today depends on how many CLI external wallets hold funds. **Fix notes:**

The finder's fix is right:
- In `external/sweep.rs`, run `utxos::fitting(&all_utxos, &Assets::new(), |_| false)` before `build::external_sweep`, as wasm's `plan_return` does.
- Bound the taken rows by transaction size and reference-script bytes. On TooLarge, take fewer.
- Print how many rows stayed and why. Today `mod.rs` prints only the outer context.

Fitting inside `external_sweep` would also be safe for its other callers: wasm passes `plan.taken`, already fitted, and `lovejoin/mod.rs:2157` and `lovejoin_pools_test` pass one row.

For `external balance`, total over the fitted rows (or in u128, for display only), list the UTxOs before totalling, and say what was left out.

The junk rows and their ~2.4 ₳ stay behind, as in the web wallet. Optionally, splitting an overflowing token's quantity over two deposit outputs would sweep everything: the ledger sums values without a bound and limits only each output to u64.

This is the same class as r4#2 (`balance.rs:39`, the remainder of `sweep --all`); fix them together, as one CLI-only commit for a patch release.

It is a high in the CLI's bounty scope, and SECURITY.md voids a report fixed on main before it arrives, so it should go to main promptly. No owner call is needed: the fix adds no refusal.
