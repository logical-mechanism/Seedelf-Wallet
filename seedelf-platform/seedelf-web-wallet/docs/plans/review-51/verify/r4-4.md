## Trace: confirmed, medium

I traced the whole path and could not refute any of it. The test fails on TREE in the three ways the finding says. When Koios answers a submit with a 5xx, with a 2xx the CLI can't read, or not within the client's 30 s timeout, the CLI ends with a plain error. That error carries no transaction id. For a 5xx it says "Koios rejected the transaction". Nothing in the CLI keeps a record of sent transactions, checks tx_status, or warns, and no doc covers it. Running the same command again after the first transaction has landed rebuilds from Koios's current rows and pays the same Seedelf another 500 ₳. The test drives that second run and sees it.

The web wallet's own koios.ts classes exactly these three answers as "maybe sent" (KoiosBusyError: "it may or may not have gone through"). The launch review graded the web wallet's form Medium (#10, under "## Medium") and fixed it there only; that review covered "the whole web wallet".

The finding holds in a slightly narrower case than its headline:
- **A full second payment:** only from `transfer` and from `sweep` with `-l` or `--asset`, on the default selection, when the run comes after the first has landed.
- **Runs with `--utxo`:** a re-run stops with "No Usuable UTxOs Found".
- **`sweep --all`:** a re-run sends only the rest, which is what the user asked for.
- **`util mint`:** a re-run mints a second Seedelf. That costs about two fees, and the ADA locked with it comes back through `remove`.
- **`remove` and `external sweep`:** a re-run finds nothing to spend (build.rs:561-562 refuses an empty list).
- **A re-run before the first is in a block:** selection is deterministic, so it takes the same input and gets a 400, also printed as "Koios rejected the transaction". A later re-run then pays again.

The default command path is enough for the medium case: an ordinary action, re-running a command the CLI said was rejected, pays the whole amount twice with no warning. Recovering it needs the recipient's help. The precondition is an honest Koios failure after the transaction was relayed, which is rare but has happened (backlog line 60 records a live 500 on a submit). It isn't high: no stranger or site can cause it, and nothing different from what's shown gets signed.

//! Chunk 51, finding r4#4: a submit the CLI can't confirm mustn't read as a
//! plain refusal. When Koios's gateway answers a 5xx, a 2xx the CLI can't
//! read, or nothing within the client's 30 s timeout (seedelf-koios's
//! koios.rs:19), the node may already hold the transaction: the web wallet
//! calls all three "maybe sent" (koios.ts's `KoiosBusyError`). So what the
//! CLI prints must name the transaction it sent, so the user can look for it
//! before running the command again, and mustn't call it rejected.
//!
//! Drives the real `transfer` run against the CLI's offline mock Koios,
//! reusing `tests/cli/harness.rs` as is. What's checked is the error `lib.rs`
//! prints (`Error: {err:#}`). The timeout case waits out the client's 30 s.
//! A second run once the first has landed is observed too, not asserted: it
//! pays the same Seedelf again.

#[path = "cli/harness.rs"]
mod harness;

use std::time::Duration;

use blstrs::Scalar;
use seedelf_cli::commands::transfer::{TransforArgs, run};
use seedelf_crypto::schnorr::random_scalar;
use seedelf_koios::koios::UtxoResponse;
use serde_json::json;
use wiremock::matchers::{method, path};
use wiremock::{Mock, ResponseTemplate};

use harness::*;

/// The payment: 500 ₳ to another person's Seedelf.
const PAY: u64 = 500_000_000;

fn pay_once() -> TransforArgs {
    TransforArgs {
        seedelfs: vec![SAMPLE_SEEDELF.to_string()],
        lovelaces: Some(vec![PAY]),
        assets: vec![],
        utxos: None,
    }
}

/// What a first run left: the words the CLI printed, the id and CBOR of the
/// transaction it sent to Koios, and the two people's keys.
struct FirstRun {
    printed: String,
    sent_id: String,
    sent_cbor: String,
    payer: Scalar,
    recipient: Scalar,
}

/// The payer holds two UTxOs of 600 ₳ and pays 500 ₳ to the recipient's
/// Seedelf; Koios takes the transaction and answers its submit with `answer`.
async fn first_run(answer: ResponseTemplate) -> FirstRun {
    let mut scenario = Scenario::start().await;
    let recipient = random_scalar();
    scenario
        .mount_credential_utxos(vec![
            wallet_utxo(scenario.scalar, 1, 600_000_000, &[]),
            wallet_utxo(scenario.scalar, 2, 600_000_000, &[]),
            seedelf_utxo(recipient, 3, 1_500_000, SAMPLE_SEEDELF),
        ])
        .await;
    scenario.mount_evaluate(1).await;
    scenario.mount_collateral().await;
    Mock::given(method("POST"))
        .and(path("/api/v1/submittx"))
        .respond_with(answer)
        .mount(&scenario.server)
        .await;

    let err = run(pay_once(), PREPROD, VARIANT)
        .await
        .expect_err("Koios never confirmed the submit, and the mock has no tx_status");
    let sent_cbor = scenario.submitted_cbor().await;
    let sent = hex::decode(&sent_cbor).expect("tx cbor hex");
    let sent_id = hex::encode(seedelf_core::build::tx_id(&sent).expect("tx id"));
    FirstRun {
        printed: format!("Error: {err:#}"),
        sent_id,
        sent_cbor,
        payer: scenario.scalar,
        recipient,
    }
}

/// The same command run again once the first transaction has landed: Koios
/// no longer lists the UTxO it spent, and lists its two outputs, the 500 ₳
/// at the recipient's register among them. Returns what the second run's
/// transaction pays the recipient.
async fn rerun_after_landing(first: &FirstRun) -> Result<u64, String> {
    let mut scenario = Scenario::start().await;
    scenario.scalar = first.payer;
    seedelf_cli::setup::inject_wallet_scalar(Some(first.payer));

    let landed = decode_tx(&first.sent_cbor);
    let mut rows: Vec<UtxoResponse> = (1..=2)
        .filter(|n| !landed.inputs.contains(&(tx_hash(*n), 0)))
        .map(|n| wallet_utxo(first.payer, n, 600_000_000, &[]))
        .collect();
    for (index, output) in landed.outputs.iter().enumerate() {
        let Some(register) = output.register.clone() else {
            continue;
        };
        let mut row = wallet_utxo(first.payer, 0, output.lovelace, &[]);
        row.tx_hash = first.sent_id.clone();
        row.tx_index = index as u64;
        row.inline_datum = Some(register_inline_datum(&register));
        rows.push(row);
    }
    rows.push(seedelf_utxo(first.recipient, 3, 1_500_000, SAMPLE_SEEDELF));
    scenario.mount_credential_utxos(rows).await;
    scenario.mount_evaluate(1).await;
    scenario.mount_collateral().await;
    scenario.mount_submit().await;

    run(pay_once(), PREPROD, VARIANT)
        .await
        .map_err(|e| format!("{e:#}"))?;
    let again = decode_tx(&scenario.submitted_cbor().await);
    Ok(again
        .outputs
        .iter()
        .filter(|o| {
            o.register
                .as_ref()
                .is_some_and(|r| r.is_owned(first.recipient).unwrap_or(false))
        })
        .map(|o| o.lovelace)
        .sum())
}

#[tokio::test]
async fn a_submit_koios_never_confirmed_names_the_transaction_it_sent() {
    // A gateway's "the instance behind me didn't answer in time".
    let gateway_504 = ResponseTemplate::new(504).set_body_raw(
        "<html><body><h1>504 Gateway Time-out</h1></body></html>",
        "text/html",
    );
    // 202 is Koios's success; this one's body stops before the id's closing quote.
    let cut_off_202 = ResponseTemplate::new(202).set_body_raw("\"5f2b", "application/json");
    // Koios takes it, and answers after the client's 30 s timeout.
    let too_slow = ResponseTemplate::new(202)
        .set_body_json(json!(tx_hash(999)))
        .set_delay(Duration::from_secs(31));

    let mut runs: Vec<(&str, FirstRun)> = Vec::new();
    for (case, answer) in [
        ("a 504 from Koios's gateway", gateway_504),
        ("a 202 whose body is cut off", cut_off_202),
        ("no answer within 30 s", too_slow),
    ] {
        runs.push((case, first_run(answer).await));
    }

    // The consequence the user meets after reading "rejected" and running it again.
    let again = match rerun_after_landing(&runs[0].1).await {
        Ok(paid) => format!(
            "run again once the first landed, the CLI paid the same Seedelf {paid} lovelace more \
             (the first paid {PAY})"
        ),
        Err(e) => format!("run again once the first landed, the CLI stopped: {e}"),
    };
    eprintln!("{again}");

    let wrong: Vec<String> = runs
        .iter()
        .filter(|(_, r)| !r.printed.contains(&r.sent_id) || r.printed.to_lowercase().contains("reject"))
        .map(|(case, r)| format!("{case}: printed {:?}; the transaction sent was {}", r.printed, r.sent_id))
        .collect();
    assert!(
        wrong.is_empty(),
        "a submit Koios never confirmed must name the transaction sent, and not as rejected:\n{}\n\
         and {again}",
        wrong.join("\n")
    );
}

## Impact: partly, low

The defect is real, but it sits lower than medium. What holds: the CLI submits with `?` at spend.rs:91 and external/sweep.rs:61. It prints no transaction id until the submit succeeds. A timeout, a 5xx or an unreadable 2xx all come out as a plain failure, and a 5xx is even worded "Koios rejected the transaction". A re-run rebuilds from what Koios shows now. Once the first transaction is on chain, the re-run picks other inputs (the first one's change among them), pays again and prints "Transaction Successfully Submitted!", so the user may never notice. No README line says to check before running again.

Why it's narrower than claimed:
(1) **The trigger.** It needs a rare Koios fault of one shape: the transaction reached a node, but no 2xx came back (a read timeout after the body went, a 502/504 the backend relayed behind, a dropped connection, a 2xx whose body can't be read). Nobody causes this, neither a stranger nor a site; it's a trusted service failing to answer. Many faults never send the transaction at all: a 10 s connect timeout, a DNS or TLS failure, a 429, a 503 that never reached a backend. The one live Koios 5xx on record (review-1.8.1.md:136, a 500 "Something went wrong") was a node refusal, not a relayed transaction.
(2) **A quick re-run doesn't pay twice.** Koios's rows show the first transaction's inputs as unspent until it's in a block. The CLI's pick is the same over the same rows: Histories::default() is blind, so it sorts by tokens, then largest ADA first (build.rs:2567), over the first 20 owned rows. The re-run therefore reuses those inputs, and the node refuses the copy as spent. The double payment needs the re-run to read Koios after the first transaction is indexed. The one exception is a wallet with more than 20 owned rows, or with ties in amount, where Koios's unordered rows (r1#1) can shift the pick.
(3) **The balance.** The wallet must still hold enough for a second payment.
(4) **What's lost goes where the user chose.** Nothing is locked, stranded or misdirected:
- `transfer`: the chosen Seedelf's owner gets the amount twice, and only they can return it.
- `sweep -l` / `--asset`: the same address gets it twice; nothing is lost when that's the user's own address, a common use.
- `sweep --all`: a re-run sends the rest of the balance to the same address, which the README already says to do ("run it again for the rest").
- `util mint`: a second Seedelf under the user's own register, whose ADA `remove` returns, so only fees are lost. Mint also prints the token name before it submits (mint.rs:104).
- `remove` and `external sweep` can't repeat.
(5) **There are ways to check, but nothing points to them.** Before a re-run, `seedelf-cli balance` shows whether the funds left. The signed CBOR is printed before the submit (spend.rs:86-89), so its id can be worked out with cardano-cli.

This is an edge case: a rare fault in a trusted service, a re-run after the first transaction is indexed, and enough balance for a second payment, with the money going to the recipient the user picked. The brief calls that low, and between low and medium it says to take the lower. Lane R1 gave the same grade to r1#2, which is this same defect. The web wallet's version (launch review #10) was medium because there the wallet itself asked for the retry, and its worker resent on its own, which undid a Lovejoin withdraw's privacy (crypto-review #4). The CLI does neither.

## Severity tiebreak: medium

Both verifiers agree on how it happens, and I re-checked it in TREE. The submit path is unchanged since CLI 0.7.0: HEAD 5175bf1d differs from the 0.7.0 tag only in docs and core's orders.rs.
- seedelf-koios/src/koios.rs:17-19 sets a 30 s total timeout.
- koios.rs:553-566 words a send error or timeout "Failed to submit transaction". It words every non-2xx, 5xx included, "Koios rejected the transaction", and an unreadable 2xx "Failed to parse submit_tx response". fee.rs:27 also calls a 2xx that isn't a bare string "rejected".
- spend.rs:91 and external/sweep.rs:61 return that error unchanged, and the id is printed only after a success (spend.rs:92-94).
- Nothing in seedelf-cli or seedelf-koios calls tx_status.
- A re-run rebuilds from Koios's current rows (transfer.rs:98-102). The blind, largest-first pick (build.rs:2567) then takes other UTxOs once the first transaction has landed, and pays again.

Graded by reach:
- **Who:** the user, by an ordinary step: running again a command the CLI said was rejected. The trigger is an honest Koios fault that nobody can cause. It's in scope because it isn't a lie.
- **Default:** it's the default `transfer` path, and `sweep -l`/`--asset`. No flag is needed.
- **Loss:** the whole payment again (500 ₳ in the scenario, unbounded in general), paid to another person's Seedelf. Only that Seedelf's owner can return it, and a Seedelf's owner is private by design.
- **Warning:** for a 5xx the CLI says the opposite: "rejected".
- **Way out:** none once paid. Before the re-run, `balance` or the printed CBOR would show it, but nothing points to either.

The impact verifier's narrowing points hold:
- An immediate re-run reuses the same inputs and gets a 400, also printed as "rejected".
- `--utxo`, `remove`, `external sweep` and `sweep --all` don't pay twice, and `util mint` costs only fees.
- The trigger is rare. The one live Koios 5xx on record (review-1.8.1.md:136) was for a transaction that never landed.

None of these brings it down to low. The 400 only postpones the double payment, and the user meets it as a second "rejected". With a 30 s timeout and roughly 20 s blocks, the first transaction has usually landed before a re-run a minute later.

Its main argument, "between low and medium it says to take the lower", is in neither COMMON.md nor the plan. INDEX.md's "the lower of trace and impact" only stands until this tiebreak. Its claim that R1 gave this the same grade holds only for R1's finder: r1#2's own trace verifier said medium.

Privacy doesn't decide it. The second spend using the first one's change is the README's admitted "Change can tie spends together", and privacy.md promises nothing about the CLI's submit.

**Decisive point:** The brief's low row needs a small cost ("A small cost in an edge case"), and the cost here is the whole payment again. It can't be got back without the recipient, and it comes after the CLI told the user the transaction was rejected. That fits medium's "A user's ordinary action loses or overpays money with no warning" word for word.

The rare trigger doesn't lower it: the web wallet's same class was graded Medium on the same trigger, twice. Launch review #10 was one. Independent review M3 was the other: "A site's submitTx answered Failure for a transaction that might land, so the site's retry could pay twice". M3 has neither thing the impact verifier used to set #10 apart (the wallet itself resending, and the Lovejoin privacy loss). Only the unreadable-2xx case on its own was graded Low (independent review L2).
