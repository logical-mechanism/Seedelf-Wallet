# e3a#1: verification

From lane E3a, graded medium by its finder.

## Trace: confirmed, medium

The finding holds as described. A site connected on the public side always talks to the dApp account, which Settings sets and which defaults to Account 1 (index 0). But every public-side Lovejoin mix is reserved under the one owner "public", whichever account built and paid it. signTx's first look reads that whole reservation, before any lookup, window or per-minute limit.

So while Account 2 (the active account) sends a mix, a site on Account 1 can name any UTxO the chain holds: Account 2's input, Account 2's collateral, or any pool box the chain draws. Pool boxes sit at a public address, so the site can list every one. For such a UTxO it hears "that a Lovejoin chain still holds". A stranger's UTxO hears "Nothing in this transaction is the public account's to sign." Following the hit on chain back to the deposit ties Account 2 to Account 1. That breaks privacy.md:334 and flows.md:438: "a signature is checked only against its own account's Lovejoin chain … Anything else … gets the stranger's answer".

I found no guard the finder missed:
- No code ties the mixing account to the dApp account. dappAccount appears only in dapp.ts, handlers.ts:356, preferences.ts, ui/sites.ts and Settings.tsx.
- handlers.ts:380 only stops an account switch while a chain is being sent, and the user switches before mixing.
- Before 955f44ad, holder() refused a site bound to an account other than the active one before signTx ran, so the probe was impossible then.

My test runs the real publicBuild and publicSubmit from Account 2. It fails on TREE because of the bug, and it passes in a copy with a three-file fix sketch, since removed.

Medium: a privacy link made by default, which any connected site can reach with free, unlimited probes. No money is at stake.

**Fix notes:**

Limit a public site's check to the dApp account's own chain. I verified this sketch in a copy, and the test then passes:
- spent.ts: `Reservation` gets `account?: number`, and `reservedSet` gets an `account` option that keeps a reservation only if `(r.account ?? 0) === account`.
- lovejoin.ts: `reserve(…, held, account?)` stores the account. checked() passes `built.account` (line 4978), publicStart passes `built.account ?? 0` (line 5223), and holdOnly (line 4769) keeps `r.account`.
- dapp.ts chainHeld: when `holder` is undefined, pass `account: await this.dappAccount()`.

Better still:
- At approval (dapp.ts:2184), check against `view.account`, the account the request was read for, as withViewKeys does, rather than the setting read again.
- Route getCollateral's chainHolds (dapp.ts:1725) through the same account-aware helper. It isn't affected today, because the dApp account's collateral can't be in another account's chain.

Scope:
- An old reservation that names no account reads as account 0's, matching ChainRecord.account's default.
- Session reservations stay keyed by index and need no account filter.

Family:
- dapp.ts:1912 is the only reader of a reservation with `only:`. The other readers (account.ts:108/173, balances.ts:329, activity.ts:597, sessions.ts, script-spend.ts:257, lovejoin.ts) leave every chain's UTxOs out of the wallet's own builds and views, which answers no site.

## Impact: partly, low

The oracle is real, and it breaks privacy.md:334's promise. Every public-side chain is reserved under the bare owner "public", whichever account pays. A site on the public side checks that same key, so a site on the dApp account hears "a Lovejoin chain still holds" for another account's chain. It hears this free, with no window and nothing counted, where a stranger's UTxO gets "Nothing in this transaction is the public account's to sign." It isn't medium, though, because the link isn't made by default. The Lovejoin tile's source starts on the private balance. That route is a mix session reserved under "session.<i>", which a public-side site never reads. A "public" chain exists only after the user turns privacy down: they pick Public account as the source, or later use Mix again from my public account (a public Bootstrap is one transaction and draws no pool box). Four more things must all hold: the wallet has a second public account; the account mixing isn't the dApp account (the default dApp account is 0); a malicious, Seedelf-aware site is connected on the public side (not a session); and that site is polling while the chain is being sent. The reservation goes once the last transaction is sent, which takes about a block for a one-box depth-2 chain and tens of minutes for the longest. No money is at stake, and the private balance stays out of it. Leaves aren't reserved, so where the boxes end up stays hidden. The chain's mixes already show the paying account on chain. What leaks is that Account 2 is the same wallet as Account 1, and that it is mixing now. That is a real link the user wasn't told of, in a narrow edge case after a non-default choice, so low.
