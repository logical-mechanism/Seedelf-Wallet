## Trace: confirmed, low

The finding holds as described. In all three of release.yml's build jobs, the job that runs `cargo build --release --locked --bin seedelf-cli` (every crate's build script and proc macro) and dtolnay/rust-toolchain@master (a moving branch) later takes RELEASE_GPG_KEY and GPG_PASSPHRASE into the same job. Both are written into step script text or argv. The same job has a token that actions/checkout@v4 leaves in .git/config. No guard stands in the way:
- The file has no `permissions:` key, and no job declares `environment:`.
- No checkout sets `persist-credentials: false`.
- `--locked` only fixes which crates build. It can't stop one already in the lock.
- No code or test in TREE reads release.yml.
The write token is not just an inference from web-wallet.yml:25-26's comment. finalize-release, which also declares no permissions, creates the draft release through softprops with that same default token, and the owner's notes record drafts with signed assets from the 0.5.0 and 0.6.0 runs. That needs `contents: write`, so every job in the file has it, the build jobs included. release.yml at tag 0.7.0 and at web-wallet/1.9.1 is byte-identical to TREE's, so the latest CLI release ran this layout.

One detail is wrong, and the truth is worse. "Edit the draft release" isn't reachable from a build job's token in the same run. The draft only exists once finalize-release runs (`needs:` all three build jobs), and a job's token dies with its job. The token can instead swap the assets of the already published releases (0.7.0's), and with the stolen key those swaps pass RELEASE.md:37-47's checks. It can also move tags. A tag pushed with GITHUB_TOKEN starts no workflow run.

It is not known. No backlog line, archived review or owner rule covers the release workflow's secrets or token. SECURITY.md:41 takes bugs inside a dependency out of the bounty; it doesn't cover our own workflow's layout. The repo's other workflows already defend against exactly this threat (web-wallet.yml:25-26 and :83-86, data-layer.yml, data-layer-deploy.yml:33: "the build runs every dependency's build script"). release.yml is the one workflow that doesn't.

Severity stays low. Who: nobody in scope. It needs a third-party compromise first: one of the 33 crates.io build scripts or 19 proc-macro crates in the CLI's Linux graph, or dtolnay/rust-toolchain's master branch. The cost, if that happens, is high and outlasts the compromise. The release key and passphrase can sign any seedelf-cli, past or future, that passes RELEASE.md's checks, until the owner revokes the key and publishes a new fingerprint. The token adds swapped release assets during the job. The compromise alone already poisons the one binary built in that run; this layout is what turns it into a key that keeps working. The way out is rotating the key. By the brief's scale this is "a missing check with no reachable harm today".

**Fix notes:**

The finder's fix is right: data-layer-deploy.yml's layout.
- **Build jobs** (linux, windows, mac): `permissions: contents: read` (top level), `persist-credentials: false` on every checkout, no secrets. They upload the unsigned binaries.
- **One sign-and-publish job:** `needs:` all three builds and builds nothing. It runs in a `release` environment with required reviewers (the owner), its deployment rule limited to tags, and `permissions: contents: write` only there.
  - Both secrets go through `env:`, never `${{ }}` inside `run:`, so they never land in the step script's text.
  - The key reaches gpg on stdin (`printf '%s\n' "$RELEASE_GPG_KEY" | gpg --batch --import`).
  - The passphrase goes through `--passphrase-fd 0` or `--passphrase-file`, never argv.
  - It also computes the hashes and signs hashes.txt.
- **What the environment adds:** today the key is a repository secret, readable by any workflow a collaborator pushes on any branch. The environment's tag rule closes that too.
- **What this doesn't fix:** a compromised toolchain action or crate still poisons the binary it builds. The fix keeps the key and the token from outliving that one run.
- **Same jobs, other findings:** delete the Windows `Get-Content` print (b1#4; in this layout Windows never sees the key). Pin softprops/action-gh-release, download-artifact and dtolnay/rust-toolchain by commit SHA (b1#5), since the signing job still runs softprops beside the secrets.
- **Family:** continuous-integration.yml has no permissions key, and its actions/checkout@v3 persists the token while setup-aiken and aiken run. It holds no secrets, so the fix is `permissions: contents: read` and `persist-credentials: false`.
- **Needs the owner:** the environment, its reviewers and its tag rule, and moving RELEASE_GPG_KEY and GPG_PASSPHRASE into it, are repository settings. The finder's `needs_owner` stands.
- **Regression test:** the test at extension/tests/r51-b1-3.test.ts passes on that layout, so it can stay to keep the layout pinned.

```
// Chunk 51, b1#3: release.yml signs the CLI with the release key, and must keep that key, its passphrase and a
// write token out of every job that runs build code. A job that runs cargo runs every crate's build script and
// proc macro, and dtolnay/rust-toolchain@master runs whatever that branch holds. A process they start outlives
// its step, so it can read a later step's script, where `${{ secrets.X }}` is already written out, gpg's
// --passphrase argument, and the token actions/checkout leaves in .git/config. With no `permissions:` key, every
// job's token gets the repository's default, which web-wallet.yml records as write. The layout that keeps them
// apart is data-layer-deploy.yml's: a read-only build job with no secrets, and the secret in a job that builds
// nothing. This test reads release.yml as text, since no YAML parser is installed, and fails while the build jobs
// hold the secrets or a write token.

import { readFileSync } from "node:fs";

import { describe, expect, it } from "vitest";

const text = readFileSync(new URL("../../../../.github/workflows/release.yml", import.meta.url), "utf8");
const lines = text.split("\n");

const indentOf = (l: string) => l.length - l.trimStart().length;
const blank = (l: string) => l.trim() === "" || l.trimStart().startsWith("#");

/** The lines under the key at `i`: everything up to the next line at the same or a shallower indent. */
function under(ls: string[], i: number): string[] {
  const base = indentOf(ls[i]);
  const out: string[] = [];
  for (let j = i + 1; j < ls.length; j++) {
    if (!blank(ls[j]) && indentOf(ls[j]) <= base) break;
    out.push(ls[j]);
  }
  return out;
}

interface Job {
  name: string;
  body: string[];
}

const jobsAt = lines.findIndex((l) => /^jobs:\s*$/.test(l));
const jobLines = jobsAt < 0 ? [] : under(lines, jobsAt);
const jobs: Job[] = [];
jobLines.forEach((l, k) => {
  const m = /^ {2}([\w-]+):\s*$/.exec(l);
  if (m) jobs.push({ name: m[1], body: under(jobLines, k) });
});

const topPermissionsAt = lines.findIndex((l) => /^permissions:/.test(l));
const topPermissions = topPermissionsAt < 0 ? null : [lines[topPermissionsAt], ...under(lines, topPermissionsAt)].join("\n");

/** The job's own `permissions:`, else the workflow's, else null: the repository's default applies. */
function permissionsOf(job: Job): string | null {
  const k = job.body.findIndex((l) => /^ {4}permissions:/.test(l));
  return k < 0 ? topPermissions : [job.body[k], ...under(job.body, k)].join("\n");
}

function steps(job: Job): string[] {
  const s = job.body.findIndex((l) => /^\s*steps:\s*$/.test(l));
  if (s < 0) return [];
  const items = under(job.body, s);
  const first = items.find((l) => l.trimStart().startsWith("- "));
  if (!first) return [];
  const dash = indentOf(first);
  const out: string[] = [];
  items.forEach((l, k) => {
    if (indentOf(l) === dash && l.trimStart().startsWith("- ")) out.push([l, ...under(items, k)].join("\n"));
  });
  return out;
}

const bodyOf = (job: Job) => job.body.join("\n");
/** Runs a crate's build code or installs the compiler: cargo, or the toolchain action. */
const buildsCode = (job: Job) =>
  /\bcargo\s+(build|install|test|run|check|clippy)\b/.test(bodyOf(job)) || /uses:\s*dtolnay\/rust-toolchain/.test(bodyOf(job));
const holdsReleaseSecret = (job: Job) => /secrets\.(RELEASE_GPG_KEY|GPG_PASSPHRASE)\b/.test(bodyOf(job));

describe("release.yml keeps the release key away from build code (b1#3)", () => {
  it("was parsed: it has jobs that build the CLI, and the release is still signed", () => {
    expect(jobs.length).toBeGreaterThan(0);
    expect(jobs.some(buildsCode)).toBe(true);
    expect(jobs.some((j) => /secrets\.RELEASE_GPG_KEY\b/.test(bodyOf(j)))).toBe(true);
  });

  it("no job that runs cargo or the toolchain action holds the release key or its passphrase", () => {
    const exposed = jobs.filter((j) => buildsCode(j) && holdsReleaseSecret(j)).map((j) => j.name);
    expect(exposed).toEqual([]);
  });

  it("every job that runs cargo or the toolchain action has a read-only token and leaves none in .git", () => {
    const problems: string[] = [];
    for (const job of jobs.filter(buildsCode)) {
      const permissions = permissionsOf(job);
      if (permissions === null) problems.push(`${job.name}: no permissions key, so the repository's default (write)`);
      else if (/write/.test(permissions)) problems.push(`${job.name}: a write permission: ${permissions.trim()}`);
      for (const step of steps(job)) {
        if (/uses:\s*actions\/checkout@/.test(step) && !/persist-credentials:\s*false/.test(step)) {
          problems.push(`${job.name}: actions/checkout leaves the token in .git/config`);
        }
      }
    }
    expect(problems).toEqual([]);
  });
});
```
