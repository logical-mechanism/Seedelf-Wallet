## Trace: confirmed, medium

The finding holds as described, and I found no guard the finder missed. A connected site's signData payload is checked only for being hex and under the size cap. readableText then refuses only C0 controls (other than tab, LF and CR) and DEL, so bidi overrides and isolates, zero-width characters, U+FEFF and C1 controls all stay in the approval's `text`. Nothing between the worker and the window changes that text. The window shows it in place of the hex, raw, in a <pre> whose `unicode-bidi: isolate` doesn't touch overrides inside it. Meanwhile the key signs the bytes as given. This works for the payment, stake and DRep keys, on the public account and in private sessions. No test covers it.

My test drives the real worker's signData and renders the window's own SignData component. It fails on TREE: U+202E, U+202C and U+200B reach the window raw. In a throwaway copy, it passes with either fix the finders propose, escaping or falling back to hex.

Severity: the literal high-row wording ("signs something other than what it shows") is met. But what's signed is a CIP-8 message: the window itself says "It moves no money", and money harm needs an off-chain party acting on the bytes. So medium, one below high. That's the finder's grade, and I'd put it at the low end of medium.

The two extra parts that e3b#1 adds also hold by trace, but they're low. First, signTx's CIP-20 note is shown raw in the window's summary. Second, the note isn't checked against the body's auxiliary_data_hash. Both are mitigated by the same window's Transaction details view, which escapes the note and warns on a hash mismatch.

// Chunk 51, finding e3a#3 (also e3b#1): a site's signData message reaches the
// connector's window with direction overrides and invisible characters still
// in it. readableText (background/dapp.ts) refuses only C0 controls but tab,
// LF and CR, and DEL, so "Pay U+202E 0001 U+202C ADA" keeps its override, and
// SignData (ui/screens/DappApprovals.tsx) shows the text, without the hex, in a
// <pre> whose `unicode-bidi: isolate` keeps it from reordering what's around
// it, not what's inside: the window reads "Pay 1000 ADA" over bytes that say
// 0001. A zero-width space makes "nonce 4<ZWSP>2" read as "nonce 42".
// Everywhere else the wallet shows a site's or the chain's text it strips or
// escapes these (siteTitle, governance.ts shownText, decode.rs shown,
// ui/tokens.ts HIDDEN). The worker's approval, rendered as the window renders
// it, should carry none of them raw: escaped as decode.rs writes them, left
// out, or the hex in the text's place. The real WebAssembly and fakes of
// Koios, as dapp.test.ts' signData case.
import { createElement } from "react";
import { renderToStaticMarkup } from "react-dom/server";
import { describe, expect, it } from "vitest";

import { type DappSession } from "../src/background/dapp";
import { DataSignError } from "../src/shared/dapp";
import { SignData } from "../src/ui/screens/DappApprovals";
import { testBalances, vectors } from "./fakes";

const PASSWORD = "correct horse battery";
const account = (words: number) =>
  vectors("cardano_account.json").find((v) => v.account === 0 && v.phrase.split(" ").length === words)!;
const OWN = account(12).preprod.receive_0 as string;
const hex = (text: string) => Buffer.from(text, "utf8").toString("hex");
const site = (): DappSession => ({ id: "r51e3a3", origin: "https://app.example.com", title: "Example" });

/** Right-to-left override, pop directional formatting, zero-width space. */
const RLO = String.fromCodePoint(0x202e);
const PDF = String.fromCodePoint(0x202c);
const ZWSP = String.fromCodePoint(0x200b);

/**
 * What changes how text reads without showing: Unicode's Cf and Default_Ignorable_Code_Point (ui/tokens.ts HIDDEN),
 * the C0 and C1 controls but the tab and line breaks the window keeps, and U+2028/2029 (decode.rs hidden()).
 */
const HIDDEN = /[\p{Cf}\p{Default_Ignorable_Code_Point}\p{Cc}\p{Zl}\p{Zp}]/u;
const KEPT = new Set([0x09, 0x0a, 0x0d]);
const hidden = (c: string) => HIDDEN.test(c) && !KEPT.has(c.codePointAt(0)!);
const named = (text: string) =>
  [...text].filter(hidden).map((c) => `U+${c.codePointAt(0)!.toString(16).toUpperCase().padStart(4, "0")}`);
/** Whether every character of `want` is in `text`, in order: the message is still there to read. */
const inOrder = (want: string, text: string) => {
  let i = 0;
  for (const c of text) if (c === want[i]) i++;
  return i === want.length;
};

async function until(check: () => boolean) {
  for (let i = 0; i < 200 && !check(); i++) await new Promise((r) => setTimeout(r, 0));
  expect(check()).toBe(true);
}

describe("a site's signData message with direction or invisible characters (chunk 51, e3a#3)", () => {
  it("is shown in the window with none of them raw, so it can't read as other than its bytes", async () => {
    const t = testBalances();
    await t.wallet.create(account(12).phrase, PASSWORD);
    await t.preferences.set({ dappConnector: true, spendRewards: false });
    const s = site();
    const enabling = t.dapp.call(s, "enable", []);
    await until(() => t.dapp.approvals().length === 1);
    await t.dapp.answer(t.dapp.approvals()[0]!.id, true);
    expect(await enabling).toBe(true);

    const messages = [
      // Reads "Pay 1000 ADA for order 77" in the window: the override reverses 0001.
      `Pay ${RLO}0001${PDF} ADA for order 77`,
      // Reads "Sign in: nonce 42".
      `Sign in: nonce 4${ZWSP}2`,
    ];
    const results: Array<{ raw: string[]; says: boolean }> = [];
    for (const message of messages) {
      const signing = t.dapp.call(s, "signData", [t.deps.wasm.cip30Address(OWN), hex(message)]);
      signing.catch(() => undefined);
      await until(() => t.dapp.approvals().length === 1);
      const a = t.dapp.approvals()[0]!;
      if (a.kind !== "sign-data") throw new Error(`a sign-data approval, not ${a.kind}`);
      // As DappApprovals.tsx renders it.
      const html = renderToStaticMarkup(
        createElement(SignData, { address: a.address, signer: a.key, payload: a.payload, text: a.text }),
      );
      const shown = /data-testid="dapp-data-message">([\s\S]*?)<\/pre>/.exec(html)?.[1];
      expect(shown).toBeDefined();
      const visible = [...message].filter((c) => !hidden(c)).join("");
      results.push({ raw: named(shown!), says: shown === a.payload || inOrder(visible, shown!) });
      await t.dapp.answer(a.id, false);
      await expect(signing).rejects.toMatchObject({ failure: { code: DataSignError.UserDeclined } });
    }
    expect(results).toEqual([
      { raw: [], says: true },
      { raw: [], says: true },
    ]);
  });
});

## Impact: partly, low

The display gap is real: a connected site can make the signData window's text read differently from the bytes it signs, and the sign window's CIP-20 note has the same gap. But no harm is reachable today, so medium doesn't hold.

1. **No money moves.** The wallet consumes no CIP-8 signature anywhere. The COSE Sig_structure (domain-separated with "Signature1" and the address header) can't be reused as a transaction witness or as a raw ed25519 signature. The window itself tells the user so: "It moves no money."
2. **The high line "signs something other than what it shows" doesn't fit.** The window shows exactly the characters it signs, in byte order. The reordering comes from control characters the site wrote into text the window labels as the site's message ("The message"). Every claim the wallet makes itself is true: which key signs, the full address, that it moves no money.
3. **None of the brief's medium lines fits.** Nothing is lost or overpaid. The "figure" is the site's own words, not a wallet figure. There is no stuck state, no privacy link and no proof claim.
4. **Harm needs three things at once:**
   - a site the user connected, acting against them;
   - the user pressing Sign, which needs the password by default;
   - an off-chain party that acts on the message's logical bytes while ignoring format characters.

   That third party barely exists. A strict parser breaks on U+202E inside a JSON string or number. Any renderer that honours bidi shows the verifier the same reordered text the user saw. Structured CBOR payloads (maps and arrays, lead bytes 0x80–0xBF) aren't valid UTF-8, so they already show as hex. I know of no CIP-8 free-text consumer that moves value, and could check none offline.
5. **The bidi trick adds little to what a hostile site already has.** It writes its own page. It can also push text below the message box's 180 px scroll with plain newlines.
6. **e3b#1's parts are lower still:**
   - The CIP-20 note is the site's words, labelled as such, and the totals come from the body.
   - The sign window's own Transaction details already escapes the note (decode.rs `shown`).
   - It also warns on a mismatched `auxiliary_data_hash` ("Its metadata doesn't match the hash in its body…").
   - A swapped metadata blob changes only public text, not value or fee.
7. **Way out:** Decline. For signTx there is also Transaction details. signData has no hex view.
8. **Owner's rules:** nothing settles it against a fix. The fix must escape the characters, never refuse the message, because the wallet refuses only what the ledger or contracts refuse.

It is in every release since 1.0.0 (fe8b7748) and isn't recorded anywhere. Grade: low, "a missing check with no reachable harm today". It belongs to a family the project has fixed everywhere else.

**Fix notes:**

The fix is display-only and adds no refusal; a refusal would break the rule that the wallet refuses only what the ledger or contracts refuse.

1. **signData:** write every character in decode.rs `hidden()`'s set as `\u{XXXX}`. `ui/tokens.ts` HIDDEN is the browser's copy of that set; use its full set plus C0/C1 and U+2028/2029. Do it in `readableText`, or show the hex beside the text whenever such a character is present. Decode with `ignoreBOM: true` so a leading U+FEFF shows as an escape too, keeping the text as long as the bytes say.
2. **signTx sign window:** pass cip30.rs `note_of`'s lines through `decode::shown`.
3. **Metadata hash:** read the note only when `metadata_hash_matches`, or show a line in the window when it doesn't match. The hash check is already in decode.rs; any new line needs short words.
4. **Family:** in the family of site text in the connector window, these are the last two members. siteTitle, governance shownText, anchor_url and token names are already handled. Lane E7b notes drepName as a neighbour, but that's the user's own anchor, not a site's text.

Suggested Vitest for the trace verifier: signData with `hex("Pay ‮0001‬ ADA")`, then expect the approval's text not to match `/[‪-‮⁦-⁩]/`. It fails today.
