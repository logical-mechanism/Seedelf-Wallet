## Checked and holds

- Index allocation within one device holds: every write of the book goes through serial(); refuseStarted only lets a review through when its index is at or past next, and save sets next to built.index + 1, so next never moves back and no two records share an index (scan sets next past every used index; Forget and Disconnect keep next).
- Two profiles of one phrase: freshIndex starts at the local next but asks the chain, then stillUnused asks again at Send, so a profile whose book is behind skips what the other used. Only near-simultaneous fundings can share an account, which keys-and-accounts.md documents.
- A reset (Remove wallet, then restore): SessionService.reset clears the scan, restoring, seen and readAt; the new book starts at 0 and freshIndex/stillUnused skip every index used on chain. scanNow pins the phrase by one-time key 0, so a scan cut off by Remove wallet writes nothing into the next phrase's book.
- Seven kept reviews share three or four session-storage keys (SESSION_OUT, _SITE_OUT, _MIX_OUT, _TOP_UP, ...). A review another window overwrote is caught at Send by its txHash (stale, never sent), and the same is true of the parts under partKey.
- Funding in parts: fundingRecords writes a record for every part before any is sent, and checks each kept part's hash and network. A later part that fails, or is maybe sent ahead of the rest, marks the rest unsent, so the funding reads short. Funding parts stay at the front of txs, because act and settle remove only replaced copies of swaps, cancels and returns, never an out.
- Stop: the orders are cancelled, then everything comes back. A funding found never funded whose parts partly landed has failed lifted, then is brought back. Parts that wait are refused by partsMayGo once the session is stopping, failed, returning or gone. A stopped mix comes back directly. Stop refuses a closed session.
- Top-ups: topUpBuild reads accountUtxos (less what was spent or is reserved), adds a fresh 5 ₳ only when no exact 5 ₳ ADA-only UTxO without datum or script is there, and always goes as one transaction. topUpSubmit re-checks sentIn, the review's age and a session brought back by hand, records the top-up before send(), and a closed or forgotten session refuses it (live).
- Disconnect, followed for a stranger's UTxO at a site session's account: it blocks Disconnect only until a return either takes it, if it pays its own way, or leaves it behind for cost. After that the session closes with leftBehind (origin kept, as privacy review 3.12/L19 settle), so a stranger can't block Disconnect for good without paying again each time.
- The connector's single-part funding: fundingState counts it landed once anything is at the account. Nobody else knows a fresh one-time address before its funding, so a stranger can't pre-seed it. A multi-part funding is matched by each part's own tx hash, which no stranger can forge.
- Site signed outputs: siteSigned records outputs by payment key hash only (key-payment headers 0-7, even). Unknown ones count as gone at Disconnect, since the site may never send them; known, unspent and unlisted ones hold Disconnect until Koios catches up.
- The restore scan's records: account_txs comes newest first (order=block_height.desc), so .at(-1) and slice(0,-1) agree on the funding. Own transactions are those that spent from the account. A payment counts as the session's only when its first contract input carries this phrase's register. Script or Byron inputs don't throw (cred null), and order candidates come only from the key's own transactions.
- Pool-launcher check: tokenAt divides by a token pool's quantity, but core's datum decoder refuses token_quantity 0 (pool.rs:200), so a hostile pool can't make every quote into its token throw.
- quoteOf, slippageKeeping, quotesTheAsk and checkAsk hold: the funding is the amount plus the DEX fee, deposits, aggregator fee and 2 ₳ margin. slippageKeeping stays strictly under the bound, and its least of 0 is unreachable (dipped needs min_amount_out < least).
- buildFunding's review figures: whole() sums each part's first payment and the first part's collateral is added back, so the review shows the parts added up. The kept first part keeps its own figures for the history, and the later parts keep theirs.
- BigInt throughout the figures (holdingOf, spare, funding sums): no wrap. Number() conversions are capped by Math.min against small constants.
- claimSubmit and backSubmit: sendRecorded records a return before submit and refuses a record that's gone. A chain's sendChain refuses what was spent since or is reserved for parts. claimBuild never puts two sessions' UTxOs in one transaction.
- runs.ts: one network's non-trap failure never stops another's. A trap locks and stops the alarm. A relock mid-run turns the rest into the unlock's run, which sends nothing. ctx.parts?.pump(...).catch(...) short-circuits whole when parts is absent.
- collateral.ts: a timeout or a network failure is a CollateralError (unreachable), 5xx and 429 are busy, other non-OK answers are refused with giveme.my's detail, and a non-JSON 200 is refused. Nothing is submitted to Koios before giveme.my answers, so marking such a failure unsent is right.
- connector.ts: the scripts are registered only when the switch is on and Chrome grants the origins, top frames only. reachOpenPages skips a page that already has window.cardano.seedelf, and a page that fakes it only keeps the wallet out of itself. Off never removes the https grant.
- The swap's manual review (swapBuild, then txSubmit) is offered only while paused and not stopping (Swaps.tsx:2510). session-back-build is called only from the by-hand and site views, so the runner and a manual return don't race through the UI.

## Notes

- Settled, new fact: keys-and-accounts.md says the scan can't find 'an index past a run of 20 unused', and that only a funding never sent leaves one unused. That run can come from retries alone. Each Send that's turned away (giveme.my down, for example) burns its index, since refuseStarted refuses resending a recorded funding and the next review takes next. So 20-39 failed Sends in a row hide every later session from a restore's scan.
- Guard with no test: Disconnect's refusal while a return's chain is being sent (sessions.ts:2536, sess.chainSendingDisconnect) is asserted by no test I found. A lock wipes the chain's progress, but the account listing still blocks Disconnect then, so the listing is the backstop.

The screens never send those, and a race between the runner's return and a manual one conflicts on inputs, so only one lands.
- Plausible, rare, no money lost (M7's corner): Disconnect (sessions.ts:2531) can delete a record whose return's history (summary) was never written. This needs a return that Koios didn't answer, or whose history write failed, and that landed, while tx_status and its feed still don't show it 20+ minutes later even though the listing and utxo_info do. The summary goes with the record, and the returned UTxO may then read as money received and be taken first by a later funding. A fix would refuse Disconnect while any return still has a summary inside REPLACED_WATCH_MS, as runAll already looks for those.
- freshIndex (sessions.ts:6204) loops with no upper bound while every probed stake address reads used. An honest server never answers that way, and strangers can't predict future one-time stake keys, so there's no reachable harm. SCAN_MOST-style cap would make it explicit.
- connector.ts applyConnector: two concurrent calls (startup's applyKept and a Settings toggle) can both see nothing registered and both register. The second throws a duplicate-ID error, which reaches the Settings reply, while the scripts stay registered. Cosmetic, not money.
- Pre-release preprod sessions only (ownStake false): siteAccount returns the session's own stake key's reward address, while the session's address carries the shared Seedelf staking part.
