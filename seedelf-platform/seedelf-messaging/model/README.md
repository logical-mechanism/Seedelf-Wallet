# The session model (54b)

A symbolic model of [protocol.md](../docs/protocol.md) §3 to §6 and §19, as built (§16), in [Tamarin](https://tamarin-prover.com) 1.12.0: first contact with the static DH, the Double Ratchet with skipped keys, the reader's rule on a cid, continuations, and the verified reveal. [session.spthy](session.spthy) is the model and [check.sh](check.sh) proves it. Chunk 54's 54b.

It checks the design, not the Rust: nothing here reads the crate. The vectors, the adversarial tests and the mutation pass hold the code to §16 ([security.md](../docs/security.md), *The session layer*); this holds §16 to its claims.

```bash
./check.sh               # every lemma, then each configuration's wellformedness checks
./check.sh m1_secret     # some lemmas
LOGS=/tmp/m ./check.sh   # keep the logs
```

It needs Docker. The first run builds the image from [Dockerfile](Dockerfile): Tamarin 1.12.0 and Maude 3.5.1, each pinned by its release's SHA-256, on a pinned Ubuntu 24.04. Every lemma then runs in its own container with no network and a memory cap (`CAP`), `PAR` at a time.

**It's heavy.** A lemma takes from seconds to 30 minutes, and up to 8 GB, and the whole run took an hour at the defaults: run it when the machine is otherwise idle. Each run gets `CAP` of memory with no swap and `CPUS` cores, `PAR` at a time, so the defaults (5, 1 core, 8 GB) take at most 40 GB and 5 cores, and `PAR=1` one run's 8 GB and a core. Tamarin's runtime would take every core otherwise, and its heap is held under `CAP`, where GHC compacts in place instead of copying. Compacting is slow, so a run near its cap slows down rather than fails; a run with no result says why it stopped, out of time or of memory, and its peak live heap.

check.sh proves every lemma above, and each configuration's wellformedness checks pass (2026-11-22). A lemma's "unless" names the only compromises that break it. Anything it doesn't name, the attacker may do at any time: hold every other key, and read, drop, reorder, replay and forge every message, as the relay can (§11).

**§1.1:**
- **x_B (the reader's key)** opens the first messages (`m1_secret` names it, and `m1_open_to_a_later_reader_key` finds it working after the reply). Stolen before the first reply reaches Alice, it takes the conversation over from her side (`reader_key_before_the_reply_takes_over`). Stolen later, it opens nothing more: `m3_forward_secret`, `m4_forward_secret`, `r1_forward_secret`, `r2_forward_secret`.
- **x_A (the writer's key)** opens nothing: no secrecy lemma names it.
- **A stolen state,** either side's, taken after its first reply, opens messages until the next reply the attacker didn't write (`initiator_state_opens_m3_and_r2`, `responder_state_opens_m3`). After that each side's next message is secret again: `m4_heals_after_a_reply_the_attacker_only_watched`, and `r2_heals_after_the_responder_state` with `-D=RESPONDER_STATE`.
- **One message key,** a skipped key the reader keeps for a message still to come, opens that message and not the next on its chain (`skipped_key_opens_only_its_message`, `skipped_key_stolen_opens_its_message`). Alone it writes nothing here, since the tag's associated data holds w₀ (`skipped_agreement`); on the wire that rests on the outer layer (assumption 2). With w₀ too, which x_B gives even stolen after the reader accepted, or a stolen state, it writes that message while the reader still waits for it (`skipped_key_and_reader_key_forge_its_message`). Each of §1.1's rows holds alone; this is two of them together.
- **Key-compromise impersonation:** the reader's own key lets anyone pose to it as any R_A (`reader_key_lets_anyone_pose_to_the_reader`), as a continuation of any of its conversations, which it labels "Continues" (`reader_key_forges_continues`), and as the owner of anyone's Seedelf in a reveal (`reader_key_forges_a_reveal`).

**§3 to §6:**
- **The static DH holds R_A:** a reader accepts a session whose A is P's key only if P started it, with the same cid, R_A, R_B and F (`static_dh_holds_r_a`). So no unknown-key share, and no replies sent to a mailbox the writer doesn't hold.
- **Both sides agree** on cid, R_A, R_B and every message (`responder_agreement_m1` to `_m4`, `initiator_agreement_r1` and `_r2`). A key stolen once the session runs can't forge into it: only a theft before the reader's first step excuses a later message, or a stolen state, which §1.1 says lets the attacker step in, and only one stolen before the message is read.
- **Continuations:** the static DH holds R_A with continuations about too: a reader accepts a first message whose A is P's key, fresh or a continuation, only if P sent it, with that cid, R_A, R_B and F, and reads only what P sent (`static_dh_holds_r_a_with_continuations`, `responder_agreement_m1_with_continuations`). So "Continues" shows only for a continuation the old other side started, unless its key or the reader's own was stolen first (`continues_only_from_the_old_other_side`), and it shows both ways. A continuation's message is secret unless the old other side's key is stolen (`continuation_message_secret`).
- **§5's rule on a cid is needed:** without it, a first message is read twice (`first_message_replays_without_the_cid_rule`).
- **Out of order** (§4.1): a message read after a later one on its chain, by the key kept for it, is read only as sent, and once (`skipped_agreement`, `skipped_each_read_once`), and both orders run (`skipped_in_order`, `skipped_out_of_order`).

**§19:**
- **The verified reveal names only its owner:** a reader shows "Verified ⟨Seedelf⟩" only if the Seedelf's owner revealed it in this conversation, which it started with this reader, unless the owner's key or the reader's was stolen first (`reveal_only_from_the_seedelfs_owner`). The proof's binding to cid, both identities, the name and the register is what holds it: an honest reveal can't be moved to another conversation, reader or name, a name the attacker minted with a copy of the register included. The reader's own key makes one for anyone (`reader_key_forges_a_reveal`), as §19.5 says.

## What building and reviewing it found

A reviewer with no context read the model against protocol.md (2026-11-21). Its findings changed both.

- **w₀ in the associated data is load-bearing.** A writer can choose A, E_A and S_A on the handle's generator and compute SK on any base, so only the tag, which needs w₀ = [x_B]p₀, ties a first message to a base its writer can use. Without it, a reader's continuation would publish [x_B]p₀ for a base the attacker chose: a static-DH oracle on the spending key. protocol.md §3 now says so. Call 13's base proof (54a′) later added a second guard on the same point.
- **A stolen x_B, before Bob's first reply reaches Alice,** takes the conversation over from her side; and the reader's own key lets anyone pose to it, "Continues" included. Both are in protocol.md §1.1 and §7 now.
- **A request the bounds push out leaves no tombstone** (§16.4, a [choice]). So after a flood of 50 requests, a re-post of a first message, with new proof of work after the relay's 36 hours and within t + 48 hours, reads again as a new request. It changes no conversation; the reader sees a request twice. Tombstoning evicted requests would close it, at the cost of a tombstone per evicted request. It's the owner's call (chunk 54's plan).
- **The `[reuse]` lemmas first helped nothing** (2026-11-22). Their guard, `K(k)`, never meets a key (*How it's built*), so no later proof could close on one; and each one split the search on every message the attacker sent. With nine in view, most of the later lemmas ran out of an hour or of 12.5 GB. Guarded on the key, each lemma takes minutes. The claims didn't change: a guard on the attacker deriving a key says at least as much as one on its sending it.
- **Four continuation lemmas stood on an undated helper** (2026-11-22). Their static DH lemma said the secret is out only if one of the two keys was stolen, not that the theft came first. A proof that the reader accepted only P's own message then couldn't close the branch where a key is stolen after the forgery, and searched on past an hour. Dated, as the sessions' `static_dh_secret` always was, the helper proves in the same 79 steps, and three of the four in under 9 minutes each. The fourth, the reader's key forging "Continues", is a trace, and its search held 7 GB within 15 minutes until it named its forgery (*How it's built*). None of the four was false.
- **m4's agreement first excused the initiator's state stolen at any time** (2026-11-22, #405), as `responder_keys4_secret` stated it. Dated all the way down, as the claim needs, its `responder_keys2_secret` took 94 minutes and 6.5 GB of live heap; at 8 GB, it ran into the crawl below and looked out of time.
- **A run near its memory cap crawls instead of failing** (2026-11-22). With the heap capped, GHC compacts the oldest generation in place once live data passes 30% of the cap, and compacting is slow: major collections took 15 to 23 s at 3 to 4 GB, against 2 s copying at 2.4 GB, and one at 5 GB hadn't finished after 12 minutes at full CPU. So a run out of memory looked like a run out of time. check.sh now says why each run without a result stopped, and its peak live heap.
- **Two lemmas were first stated false.** `r1_forward_secret` and `r2_forward_secret` excused a theft of Bob's key only before he accepted Alice's own F. With Bob's key, the attacker writes another first message with her cid, p₀, A and w₀ ([x_B]A and w₀ are its to compute), Bob accepts it and replies under keys it knows. That's §1.1's key-compromise impersonation, which `reader_key_lets_anyone_pose_to_the_reader` shows. Their excuse now names a theft before Bob accepted any first message, as their claim in this README always said. Found while proving them (2026-11-22), from where the search went.
- **A stolen message key writes nothing alone** (2026-11-22). Its trace lemma was first stated the other way, that a kept skipped key lets its thief write the message it stands for, as in the Double Ratchet with public associated data. Tamarin found no such trace: the tag's associated data holds w₀, so the key alone can't make a tag the reader takes. Stated next without any excuse for the key, the agreement was false the other way: x_B stolen after the reader accepted gives w₀ = [x_B]p₀, and with the kept key the attacker writes that message. `skipped_agreement` now names exactly that pair. A fresh-context review then showed the key-alone half is the model's, not the wire's: once the inner layer is visible, the key and its salt give the envelope's outer scalar o, and [o]w₀ gives w₀, and AES-GCM's tag can be redone without the associated data. On the wire it rests on the outer layer (assumption 2).
- **The model's own first version** let a stolen state open nothing: the attacker decrypted only with the associated data, and no state reveal carried w₀, its one part not on the wire. Decryption is key-only now, as AES-GCM allows, and each state reveal carries w₀.

## What the model assumes

Where a symbolic model is weaker than the protocol, or this one narrower. A reviewer should read these first.

1. **Perfect cryptography.** Tamarin's attacker controls the network and computes only what the equations allow: Diffie–Hellman in a prime-order group, where [a]P and [b]P never give [ab]P; AES-GCM, read with the key alone and accepted only under its key and associated data; HKDF and HMAC as one-way functions. Nothing about bounds, timing or side channels.
2. **No outer envelope.** The attacker sees every inner message, F, cid and headers included. That gives it more, since the outer layer authenticates nothing: anyone can seal to a register. But one thing the outer layer shows goes too: the envelope's register ([o]p₀, [o]w₀), whose o comes from the message key and the inner layer's salt (§16.2). Two claims rest on the outer layer and go unchecked here:
   - **§1.1's "x_B opens nothing Bob sent"** when x_B is stolen before Bob reads the first message. Bob's replies are then keyed to the attacker's ratchet key, and only their seal to R_A (x_A) hides them. So `r1_forward_secret` excuses a theft before Bob accepts.
   - **A kept message key, stolen alone, writes nothing** (`skipped_agreement`). Here its tag needs w₀, which the attacker lacks. On the wire, whoever sees the inner layer gets o from the key and the salt, and w₀ from [o]w₀; and AES-GCM's tag can be redone without the associated data from one genuine ciphertext and the key. What keeps a key thief from both is the outer layer, which only x_B or the device opens, and either gives w₀ anyway. Found by the follow-up's review.
3. **Handles are root registers,** (G, [x]G), one per principal. The attacker can compute [x]P for any P it knows the discrete log of, as it can over a Seedelf datum's own generator. Several registers of one key, and their sums, aren't modelled; §11 lists the link that sums give.
4. **The base a reader accepts is an honest writer's p₀, or G^k for a k the attacker chose.** It was the model's main restriction; since calls 12 and 13 (54a′), the reader enforces it.
   - **Why it's there.** The reader publishes [t]p₀, its ratchet key, on whatever base the writer chose. With p₀ an arbitrary term, Tamarin's search never closes.
   - **Why nothing is lost.** Two rules tie a first message to a base its writer can use (protocol.md §3). F's base proof shows p₀ = [b]g_S for the handle named in `to`, so its writer knows b: over the model's one generator G, that base is G^k. And the tag's associated data holds w₀ = [x_B]p₀, which the attacker knows, without x_B, for G^k through the handle, and for an honest conversation's base once w₀ is out (a stolen state, or a continuation). A continuation carries no proof, but must be on one of the reader's own conversations' bases (§6). All of these are in the model. With x_B, the reader is compromised, and every lemma lets the attacker win there.
   - **What's left out:** a base proved over another register of x_B than the root one (3). Its writer knows b over that register's generator, so it gains what a G^k session gives. That's argued, not checked. The proof's own soundness is the crate's tests' (54a′), not the model's.
5. **Every point is valid.** The symbolic group has no identity and no small subgroup, so §3's point checks are the code's and the tests' (54a), not the model's.
6. **A bounded conversation:** one first-contact message, two full round trips (m1, r1, m3, r2, m4), and one continuation link (a continuation isn't continued again). Out of order is one chain of two messages read either way (`-D=SKIPPED`), with no later step after it. MAX_SKIP, the requests' bounds, every clock (the 48-hour window, a skipped key's 48 hours, tombstones, expiry) and proof of work aren't here: they're counters and times, which the tests and the mutation pass cover.
7. **§5's rules are one restriction:** a reader takes a given cid's first message once. That's what the cid table, the tombstones and the window aim at, and the model shows it's needed. The code keeps it, but for the evicted-request gap above.
8. **Requests are read eagerly.** 54a's tests show replying builds exactly the state eager processing would (§16.4).
9. **Reading is two rules,** deriving the keys from the header, then authenticating. A message that fails leaves the model's state stuck where the code leaves it unchanged, which removes only traces in which the failure changed nothing.
10. **ENCRYPT's salt is left out.** A message key is used once in the model, and the salt is a net for a key used twice (§4.2), which only a rollback does. The model has no rollback.
11. **State theft:** each side's record after its first reply, taken once, then or later, which also stands for an old copy: the initiator's in the sessions' configuration, the responder's in its own (13). Not modelled: both at once, and a state before the first reply. One message key alone is a skipped key the reader keeps, taken once (`-D=SKIPPED`).
    - **Some lemmas name the initiator's state where it opens nothing:** `responder_keys2_secret` and `r1_forward_secret`. Tamarin finishes them only that way; without the excuse it has to refute every branch the state would end, and ran past 12 GB. They still say everything about traces where no state is stolen, and `responder_keys2_secret` names only a state stolen before the attacker knew the key, which m4's agreement needs. That costs Tamarin an hour and a half and 6.5 GB of live heap, so check.sh gives that lemma its own room (the `// check.sh:` line above it).
12. **F is one value bound into SK, and through it into every key:** cid, t, `replaces`, p₀, A and E_A. `t` is any public value. `to` and its base proof (call 13, 54a′) are left out: `to` changes only a label, and what the proof gives the reader, a base its writer can use, is assumption 4. The first-contact stamp (call 12) sits after F, and it and the envelope's outer scalar (§4.1) are about spam and unlinkability, which no lemma here claims (2, 6).
13. **Six configurations,** since Tamarin's search grows with every rule that publishes something, and with every compromise. Each lemma is proved where its own compromises are.
    - **The sessions** steal long-term keys and the initiator's state, and have no continuations. Their attacker misses what a continuation publishes: fresh powers of p₀, a message under a key it can't derive, and the old identities. Of those only w₀ isn't otherwise public, and in the protocol a continuation is sealed to the other side, so no one else sees it there.
    - **The responder's state** (`-D=RESPONDER_STATE`) is the sessions with the responder's state stolen instead of the initiator's. With both in one model, Tamarin ran past 14 GB on the third key; a lemma about one side's state doesn't need the other's.
    - **The continuations** (`-D=CONTINUATIONS`) have no ratchet and no state theft. Their attacker misses the ratchet's fresh powers of p₀ and its ciphertexts, which no continuation's SK depends on.
    - **The cid check** (`-D=NO_CID_RULE`) is the sessions without §5's rule.
    - **The reveal** (`-D=REVEAL`) is first contact, Seedelfs on chain and the reveal, with no ratchet: the reveal goes in the clear, where the protocol sends it inside the ratchet, so its attacker sees more than the real one. Its claim is about who could have made the proof, which needs no ratchet.
    - **Skipped keys** (`-D=SKIPPED`) are the sessions up to the first reply, then the initiator's next chain with two messages, and the kept key stolen; no later step and no state theft. Their helpers are the sessions' own, proved again there.
14. **The verified reveal's proof is two constructors** (`-D=REVEAL`, protocol.md §19): `prf1` the real branch, made with the key of A and of the Seedelf's register, `prf2` the other, made with w₀'s, each binding cid, p₀, A, w₀, the name and the register. The reader checks one by equality, as the real check's equations hold exactly then, with its witness a principal's key: any principal's for the real branch, its own for the other. A proof by a key no principal holds verifies only for registers of that key, so for no principal's Seedelf, and the lemma is about a principal's; the attacker still uses any key it steals. Not modelled:
    - **the proof's soundness,** which the abstraction assumes: the Cramer–Damgård–Schoenmakers argument, the crate's tests, a mutation pass and vectors reproduced from protocol.md alone (security.md, *The verified reveal*);
    - **its deniability,** that the reader could have made it, so it convinces no one else: a claim about what a third party can tell apart, which a trace lemma can't state (it would need Tamarin's observational equivalence);
    - **the chain read** (§19.4's step 4): a Seedelf's name holds one register for good here, so a Seedelf that moves owner, and the fresh read that catches it, are the wallet's and its tests';
    - **only after the first reply** (§19.1): the initiator reveals at any time after it starts, which gives the attacker more.

## How it's built

- **Rules,** following §16: `I_*` are the initiator's steps, `R_*` the responder's, `C_Derive` and `C_Send_*` a continuation by either side, and `R_Label_*` the reader's "Continues" match, judged when the request arrives (`judged_on_arrival`). `Seedelf` and `Seedelf_attacker` put names on chain, `I_Reveal` sends a reveal and `R_Check_reveal_*` check one; `I_Send_m3_first` and `_second` send a chain of two, and `R_Read_m3*` read it in either order, keeping a skipped key. `Reveal_ltk`, `Reveal_state_initiator`, `Reveal_state_responder` and `Reveal_skipped_key` are the compromises.
- **No step raises received points to a power on more than two bases,** and no step publishes a key it computed from a point it was given: reads are split into deriving the keys, then authenticating, and a continuation into deriving, then sending, once per kind of base. Tamarin's precomputation and search don't finish otherwise.
- **Each step's root key and chain key are proved secret one step at a time** (`keys1_secret` to `keys4_secret`, `heal_keys_secret`, `responder_keys2_secret` and `_keys4_secret`), and the initiator's agreement lemmas too. Each is a `[reuse]` lemma the later ones in its configuration assume, proved in its own run; check.sh runs them all. In the continuations, `static_dh_secret_with_continuations` and `static_dh_holds_r_a_with_continuations` do the same for the static DH and its hold on R_A.
- **A `[reuse]` lemma's excuse is dated** as the lemmas standing on it need: `static_dh_secret` and `_with_continuations` name a theft before the attacker knew the secret, so a proof that a message is forged only after a theft closes on them. Undated, they closed nothing that needed the order (*What building and reviewing it found*).
- **A keys lemma guards on the key itself,** `KU(rk)` and `KU(ck)`, the attacker deriving that key, so a later proof that reaches the key closes there. Two other guards fail, and the first version had both:
  - **`K(k)`** never fires: in a lemma, `K` is the attacker sending a message into the protocol (Tamarin's ISEND), and a key is never sent. It only split the search on every message the attacker sent.
  - **`KU(k)` with k = rk or ck** fires on every term the attacker derives, and the equality splits the search on each one.
  - **`keys4_secret` is the exception:** in the key-guarded form Tamarin didn't prove it in two hours at 12 GB, in the `KU(k)` form it takes minutes. So it's stated that way, `keys4_secret_guarded` restates it guarded on each key (proved from it in 21 steps), and the lemmas after see only the twin.
- **An all-traces lemma sees only the `[reuse]` lemmas its proof rests on** (`hide_lemma`), so the others cost it nothing. Hiding a lemma only drops an assumption. **A trace lemma sees them all:** they cut every branch where the attacker would build a message it has no key for. The continuations' two "Continues" traces are the exception, hiding their helpers as they always have.
- **Each trace lemma names its trace step by step:** `executable` the whole conversation, message by message, and the others the honest exchange up to their theft; `reader_key_before_the_reply_takes_over` with no reply from Bob at all, and `reader_key_lets_anyone_pose_to_the_reader` on a base and a cid no honest initiator used. `reader_key_forges_continues` names its forgery too: x_B stolen after an honest conversation, then a continuation of it on the old base with E = S = G, which any point would do. Naming more only narrows what the lemma says exists, and it keeps Tamarin's search on that trace.
- **The responder's side stands on lemmas about the first message:** `static_dh_secret` and `static_dh_holds_r_a` for its agreement, and `responder_accepted_the_initiators_f` for its keys, since `responder_keys2_secret` and `_keys4_secret` name the initiator's own F. In the continuations, `static_dh_holds_r_a_with_continuations` carries both the agreement and the label.
- **A tactic, `states_then_keys`,** ranks the goals of the lemmas Tamarin's default ranking stalled on: the protocol's states first, so a `[reuse]` lemma has the rule instances it matches, then what the attacker knows of fresh values and of keys, Diffie–Hellman case splits late, and how the attacker built a message last. A ranking changes how long a proof takes, never what it proves.
- **`KeyOn(P, p₀, A)`** is an observer rule that publishes nothing. A lemma can't write "A = [x_P]p₀" with a power in its formula, so it says KeyOn.

## Why Tamarin and not ProVerif

The plan named ProVerif by default. ProVerif takes Diffie–Hellman as an equation, and the registers need it with any point as the base: p₀ is itself a power of G, and w₀, E_A and the DH outputs are powers of p₀. Its completion of `exp(exp(P, x), y) = exp(exp(P, y), x)` didn't finish on a one-line model. Tamarin's built-in theory takes any base.
