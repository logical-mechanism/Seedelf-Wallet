# Lovejoin transaction coverage

These modules extend the existing v2 template scenarios. Run `./check.sh lovejoin-any-tx`;
its modules are also imported by `Lovejoin.lean` (the `Lovejoin/Every/` ones below aren't: run
`./check.sh lovejoin-every`). A Blaster `Valid` is an SMT result,
not a kernel proof term. The CEK controls are concrete checks, not a substitute for the
symbolic results. The template and its extracted bytes must still match the launch under
review, and transaction validity and execution budgets are ledger assumptions.

## Complete mix_box behavior in the V3 ledger model

`BoxPurposesAll.every_context_iff` is a kernel-checked characterization of the
compiled `mix_box` template for every typed V3 `ScriptContext` and any template
parameter. It has no fixed limit on inputs or withdrawals. For a spending purpose,
it finds the first input whose encoded reference matches the spending reference. A
missing match errors; otherwise a non-inline or malformed box datum is recoverable,
while a well-formed inline box requires a withdrawal for the mix_logic script
credential. The withdrawal amount and all unrelated transaction fields are arbitrary.
All five non-spending purposes error. The theorem characterizes eventual CEK success;
ledger execution budgets can still reject a transaction before an eventual result.

The proof follows the compiled input and withdrawal loops by induction (`BoxSearch`
and `WithdrawSearch`), covers all inline datum shapes (`BoxInlineAll`), and connects
the result to typed ledger encodings (`BoxCover`, `BoxSemantics`). Its guarded axiom
check permits only `propext`, `Classical.choice` and `Quot.sound`; in particular it
does not use Blaster's SMT axiom. `BoxAllControls` runs long concrete searches. The
16 shape lemmas in `BoxMalformedShapes` are generated by
`python3 gen-lovejoin-box-shapes.py`.

This is complete behavior for the individual mix_box script in this ledger model,
not a proof of the whole protocol: actual safety still relies on the ledger running
mix_logic for the withdrawal, on mix_logic's own behavior, and on the applicable
ledger and cryptographic assumptions.

`PurposesKernel.reference_holder_every_context_errors` also proves, with the same
allowed axioms, that the compiled reference holder errors for every typed V3 script
context. `PurposesKernel` additionally proves that mix_logic, one_shot_mint and
fee_contract reject their unsupported purposes, with arbitrary transaction fields
and purpose payloads. `LogicPublishKernel.publish_iff_registration` characterizes
mix_logic publishing over arbitrary raw certificate data: only constructor-zero
certificates pass. Its withdrawal handler and one_shot_mint's mint handler are
characterized in `Lovejoin/Every/` (below).

## Complete mix_logic and one_shot_mint behavior (`Lovejoin/Every/`)

`Lovejoin.Every.Readable.mix_logic_accepts_iff` characterizes the compiled `mix_logic`
template, at any pool NFT policy and the name `lovejoin` (the one every v2 launch mints), for
every typed V3 `ScriptContext` whose reference inputs' values the ledger accepts: it returns unit exactly when `mixLogicAccepts` holds, in the Aiken
source's terms.

- A withdrawal passes by `withdrawOk`. The redeemer is an `Owner` or a `Mix`, and
  `read_reference_datum` finds the reference datum. An Owner then needs `validate_owner`
  (`validateOwner`): at least one box, and each box's proof passes schnorr.ak's `verify`
  against `ctx`. A Mix needs `validate_mix` (`validateMix`): at least two boxes and as many
  proofs, then `walk_outputs` (`walkOutputs`), then at most 255 boxes, then each box's proof
  passes sigma_or.ak's `verify_pre` (`verifyPre`).
- A certificate passes exactly when it is a `RegisterCredential`.
- Every other purpose errors.

`Lovejoin.Every.Readable.one_shot_mint_accepts_iff` does the same for `one_shot_mint`, at any
seed and reference holder, for every context whose mint and output values the ledger accepts.
A mint passes by `launchOk`:
- exactly one token under the policy;
- the first output that passes `output_at_reference_holder` (the holder's script, no stake
  credential, no reference script, one of the token) has an inline `ReferenceDatum`;
- the seed is spent, the name is `lovejoin`, the quantity 1, and the datum passes `datum_sane`
  and `token_sane`.

Every other purpose errors. Run `./check.sh lovejoin-every` (16 GB, 30 min per module by
default). How these proofs are built, and how to change one: [`Lovejoin/Every/README.md`](../Every/README.md).

Those two are the results to cite: their hypotheses are value rules the ledger enforces. The
`_valid` forms take the ledger model's whole `validScriptContext` instead, which is stricter than
the ledger. Its `isBalanced` has no term for deposits, refunds or withdrawals, so it rejects
every real `RegisterCredential` (a deposit) and every Owner or Mix that withdraws a non-zero
reward balance; the `_valid` forms say nothing about those.

These are kernel-checked, with no list-length bound and no step limit: the guarded axiom checks
permit only `propext`, `Classical.choice` and `Quot.sound`. The method differs from the
Blaster families above, in two layers:
- **The bytes.** Each region of the compiled code is read back as a Lean function over raw
  `Data`, `none` for the script's error, in the compiled evaluation order. One CEK theorem per
  region says the program computes it, both directions at once; loops are by induction over
  their lists. `Lovejoin.Every.every_context_iff` and `mint_every_context_iff` put them
  together as `withdrawResult` and `launchResult`: what the bytes do, written as Lean.
- **The source's terms.** `Readable*.lean` restates those functions over the ledger's typed
  `TxInfo`, one Aiken function at a time (`readReferenceDatum`,
  `collectWellFormedMixInputs`, `validateOwner`, `RefDatum.boxValue`, `outputAtScript`,
  `walkOutputs`, `verifyPre`, `validateMix`, `launchOk`, `datumSane`), and proves each equal
  to the raw function on `IsData.toData` of the typed value. `walkOutputs_eq` reads
  `walk_outputs` whole: at least `n` outputs, each of the first `n` a box out, none after them
  passing `output_at_script`.

What the restatement makes visible:
- **Recompressed points.** The compiled code stores a Mix statement's points compressed, so
  each branch's equations use `uncompress(compress(A'))`, not `A'` (`branchHolds`). No crypto
  fact is assumed to remove it.
- **`box_value`'s edges, as the bytes have them.** No ADA entry at `box_lovelace = 0`, and no
  token at `token_quantity = 0`. one_shot_mint's `datum_sane` rules both out at launch.
- **The ledger's own rules, as hypotheses where they're used.** Sorted values and maps turn
  the program's ordered searches into the ledger's `valueOf` (`ReadableBase.lean`). Nothing
  else about the transaction is assumed.

The same limits as above apply: IOG's CEK model, on our fork; the crypto builtins,
`serialise_data`, `byteStringToInteger` and `xorByteString` opaque (`serialise_data` and
`xorByteString` through our PlutusCoreBlaster fork's aliases, `byteStringToInteger` upstream's
too), so a result holds for any interpretation of them, which says what the bytes check, not
that the crypto is hard to break; eventual CEK success, not execution budgets. The rest of
where the claim stops is in [CLAIMS.md](../../CLAIMS.md).

## Withdrawal-handler progress

The complete results above supersede this section's partial ones, which stay as
independent cross-checks.

`LogicLength.length_all` proves the compiled list-length loop for arbitrary data
lists. `LogicInputRefs.ledger_refs` proves that the Owner input-reference traversal
returns every typed input reference in order. The Owner proof parser and both levels
of the Mix proof parser are proved for arbitrary lengths, including an error
continuation for arbitrary raw Mix proof and branch data.

`LogicProofPairs.wrapper_all_partial` proves the compiled pairwise verification loop
for lists of arbitrary lengths and an arbitrary supplied verifier closure, including
verifier errors. Its success condition is equal list lengths and success of each
aligned verifier call (`allPairsPartial_true_iff`). This isolates the shared Owner/Mix
pairing loop; connecting the supplied closure to the actual cryptographic verifier
and the whole validator remains open.

`LogicInputHelpers.supported_with_compiled_helpers` proves that the compiled box-input
collector handles arbitrary interleavings and numbers of well-formed boxes, key inputs,
foreign-script inputs, and mix-script inputs with no datum or a datum hash. It keeps
the well-formed box datums in order. It also skips non-constructor inline data at the
mix script. This uses the actual compiled selector and byte classifier closures;
malformed constructor-shaped inline data and the connection to whole-validator
acceptance remain to be proved.

`LaunchSeedSearch.search_ledger` proves that the one-shot policy's compiled seed
search finds exactly the matching output reference in any typed input list, with any
number of other inputs. `LaunchSeedSlots` provides an adapter for connecting it to the
validator. The general mint, output and datum checks and whole-validator composition
remain open; the seed-search lemma by itself does not establish launch correctness.
`LaunchOutputSearch.search_all` separately proves the compiled output traversal finds
the first match for an arbitrary output list, conditional on the result of its extracted
destination predicate. The destination predicate itself still needs a general proof.

`LogicOwnerNoCarrier` and `LogicMixNoCarrier` prove whole-validator rejection for
**every raw proof list** when no reference inputs exist, for any pool policy. Their
typed no-carrier variants cover arbitrary interleavings of empty-value and ADA-only
reference inputs when the NFT policy sorts after the empty ADA policy.
`LogicOwnerShape` proves independently that any successful typed Owner withdrawal
has a proof list made entirely of the expected two-bytestring encodings, for arbitrary
transaction fields. This is a structural result, not proof of ownership.
`LogicMixShape` proves that any successful Mix withdrawal has an outer proof list
where every proof contains exactly one branch list, including when malformed raw proofs
precede it. It does not yet establish the shape or cryptographic validity of every branch.

`LogicPolicyLookup` and `LogicNameLookup` prove the compiled ordered lookups for
arbitrary prefixes. `LogicCarrierFilterExact` proves that, for the represented asset
map layouts, the filter retains exactly the references with target NFT quantity one.
`LogicWrongQuantity` and `LogicDuplicateCarrier` connect this to the full validator for
any raw proof list. `LogicVariableNecessary` proves that successful Owner and Mix
withdrawals require exactly one such carrier even when each candidate has independently
varying map prefixes and suffixes. These results require the stated ordering assumptions
and an explicit target policy and name entry for each candidate; they do not cover every
possible reference-input value layout. `LogicBadCarrierDatum` proves that the sole
carrier must not have a missing or hashed datum, for either withdrawal and arbitrary
proof data in the same independently varying map family.

`LogicCarrierCover` combines target-present, absent-name and absent-policy search
shapes, including arbitrary unchecked map tails. `LogicLedgerValueCover` proves that
every reference input accepted by the V3 ledger model falls into this cover. Thus
`LogicLedgerCarrier` proves, for fully valid V3 contexts and arbitrary raw Owner or Mix
proof lists, that successful mix_logic execution requires a reference output containing
the target NFT entry at quantity one. `LogicValueOf` strengthens this to quantity one
according to the ledger model's `valueOf`. `LogicSortedValue` and `LogicLedgerUniqueness`
connect that compiled search to the ledger model's ordering rules: a successful Owner or
Mix execution with valid reference inputs requires exactly one actual reference input
with ledger `valueOf` equal to one for the NFT, for any raw proof list. This is a transaction-local
condition; it does not establish global NFT supply or the remaining authorization checks.
The cover classifies how the compiled ordered search behaves even for unsorted
unchecked tails; it does not claim those tails cannot contain duplicate keys.

`LogicLedgerInline` extends the carrier result to all ledger-valid reference values:
the unique NFT-bearing input must carry an inline datum. `LogicInlineMalformed` proves
that this datum must have a constructor shape, rejecting integers, bytestrings, lists and
maps for both Owner and Mix and arbitrary raw proof lists. Its constructor tag and fields
are not yet characterized, and this is not yet an authorization proof.

`ReferenceHolderPersistence` connects the reference holder's compiled rejection to a
transaction-level consequence: an accepted transaction cannot consume an input at the
holder credential, assuming the ledger routes it to this exact script. The reference-specific
form additionally assumes correct UTxO resolution. This does not establish launch
correctness, chain-level persistence, or global NFT supply.

`LogicBoxComposition` joins this result to mix_box on the same TxInfo. A successful
well-formed box spend requires a matching withdrawal; if the explicitly assumed ledger
routing executes the specified mix_logic template successfully, the transaction must
contain a reference input whose ledger `valueOf` for the NFT is one. This is a necessary
condition, not yet a complete proof of Owner or Mix authorization.

`LogicProofBoundary` proves both branches reject a non-constructor proof after any
structurally valid proof prefix, and `LogicMixBoundary` covers a non-constructor Mix
branch after arbitrary valid proof and branch prefixes. `LogicLongControls` and
`LogicWrongQuantityControls` exercise long proof lists and zero, one and multiple
carriers; these are concrete evaluator checks and do not assert ledger validity.

The complete Owner and Mix proofs still require general box-input filtering, proof
verification, Mix output traversal, and their connection to the whole validator.
Protocol-level composition, cryptographic assumptions, ledger routing and execution
budgets also remain to be handled beyond the necessary-condition theorem above.

## New scenarios

| Module | Transaction cases |
| --- | --- |
| `FeePurpose` | The fee template rejects minting, rewarding, certifying, voting and proposing for arbitrary context fields. |
| `LogicEmpty` | Owner and Mix fail with a single key input, no box, no proofs, and one pool reference input; Mix also fails with a single possible box and no proofs. |
| `LogicControls` | A malformed, long proof exhausts a 5,000-step run and reaches error by 20,000 steps. |
| `OwnerOne` | One box and one key input: invalid proofs fail for arbitrary outputs and input references; a valid proof passes when the policy is nonempty. One carrier reference, with fixed value and datum fields. |
| `OwnerControls` | A real proof passes; a changed proof, output, or input reference fails. |
| `BoxGate` | One input precedes the box; no withdrawal, a different script, a matching script, and a key followed by the matching script. Also characterizes malformed byte pairs when no withdrawal exists. |
| `BoxBoundary` | Missing own input fails; no datum and a datum hash are recoverable; arbitrary input and withdrawal suffixes after matches. |
| `BoxSuffix` | One input and one different script withdrawal precede the matches, with arbitrary suffixes; no withdrawal with arbitrary inline data and arbitrary later inputs; key plus different script do not authorize the box. |
| `BoxDatum` | Any inline `Data`, with no withdrawals, is recoverable exactly when the datum is not a well-formed box. |
| `BoxControls` | Eleven concrete evaluator checks for authorized, unauthorized, malformed, non-inline and missing-input transactions. |

The accompanying `*Controls` modules run passing vectors and changed transactions.
`Owner3` and `Owner4` are generated by `python3 gen-lovejoin-anytx-owners.py`. The
three- and four-box Mix families and their controls are generated by
`python3 gen-lovejoin-anytx-mixes.py` and `python3 gen-lovejoin-anytx-mix-outputs.py`.
The fee recovery behavior applies to the datum delivered to the spend handler: a hash
with a witness and an inline datum can both resolve to it. These are explicit scenario
families; their carrier, input and output list shapes remain fixed except where stated.

The input search cases with a prior input assume its reference differs from the spent
reference. Every other TxInfo field, the redeemer, resolved datum, values and addresses
that the relevant case does not inspect are arbitrary `Data`. Some scenario proofs also quantify over arbitrary list suffixes. The separate
kernel-checked mix_box result above covers arbitrary numbers of preceding inputs and
withdrawals. A gate acceptance only establishes that
mix_box lets the spend through; safety also requires the ledger to invoke mix_logic for
the withdrawal and mix_logic itself to accept the corresponding proof and outputs.

## Owner verifier progress

The complete results above supersede this section too: `mix_logic_accepts_iff` is the
whole validator, Owner and Mix, and `one_shot_mint_accepts_iff` the whole launch, with no
list bound. What follows stays as independent cross-checks.

`LogicOwnerBoundaryPartial` joins the compiled Owner count gates, transaction hash,
and pairwise Schnorr verifier for arbitrary-length aligned lists at an internal
execution boundary. A true result there requires at least one box, the same number
of proofs and boxes, and a successful Schnorr equation for every pair, bound to
all input references, all outputs and the mix-script hash. Its verifier model
covers arbitrary point and scalar bytes: invalid encodings or scalar values cause
an error. The theorem still assumes the relevant execution environment, transaction
hash, collected boxes, and aligned constructor shapes; it is not yet a theorem
from full-validator success.

`LogicInputExtended` covers key inputs, foreign scripts, missing and hashed
datums, and every form of inline datum, including malformed constructors and
invalid point lengths. `LogicInputCover` proves that every typed V3 ledger input
list has an order-preserving representation in this model and connects it to the
compiled collector wrapper. `LogicOwnerShapesJoin` combines that input cover with
whole-validator Owner acceptance to derive the aligned datum and proof shapes.
These results still need to be connected to the Owner boundary as part of a single
whole-validator execution proof. `LogicOwnerEntry` proves that the compiled collector/dispatch junction reaches
the Owner prologue on an arbitrary CEK stack, and `LogicOwnerProgramBoundary`
connects acceptance of the surrounding program to the transaction-bound proofs.
That program-level theorem still assumes that execution reaches the junction,
that its environment has the specified values, and that its continuation rejects
false; those hypotheses are not yet proved from full-validator execution.

The launch seed and output search loops have unbounded subterm proofs, but the
whole launch theorem remains open. A direct whole-launch seed attempt exceeded a
16 GB memory limit; it needs further decomposition. Mix proof and output checks
remain bounded to the stated layouts.

## Remaining safety work

For mix_box, mix_logic, one_shot_mint and reference_holder, the complete results above
leave no transaction layout to cover: the scenario families here, with their fixed input,
reference and output layouts, stay as cross-checks. fee_contract has no such result, only
its rejected purposes (`FeePurpose`, `PurposesKernel`) and fixed layouts (`FeeMix`,
`FeeSpend` and `FeeRecovery` here, more in `Template/` and `Audit/`), and it's out of the
claim: no Seedelf transaction uses it. The audit suites add more layouts, but their own
status and assumptions need checking before relying on them. These proofs say what each
script checks, not that the cryptography can't be broken, within the limits
[CLAIMS.md](../../CLAIMS.md) states.

## Additional transaction matrix to verify

These were test or proof targets, not results. Whether mix_box, mix_logic and one_shot_mint
accept, in any transaction the ledger can form, is now the complete results above, so the
rows stay as cross-check targets, and the *Fee shard* rows as fee_contract's, which is out
of the claim. Some have narrower counterparts in the existing `V2/` and `Audit/` modules;
the purpose here is to vary their surrounding transaction and ordering, then check the
results against those modules' actual hypotheses.

- **Input search:** no inputs; spent reference first, middle, last, or absent; many unrelated
  key and script inputs; unrelated inputs after the box; different output indices under the
  same transaction ID; repeated references in malformed contexts; non-inline and malformed
  entries before and after valid boxes.
- **Withdrawals:** no withdrawal; matching script first, middle, last; key credential with
  the same bytes as the script hash; unrelated scripts before and after the matching key;
  different amounts including zero; repeated keys in malformed contexts.
- **Owner:** zero boxes; one to four boxes in different input positions; more than four;
  too few or too many proofs; exchanged proofs; reused proof with a changed output address,
  value, datum or reference script; added, removed, reordered or replaced input references;
  duplicate point pairs with different references; unrelated inputs inserted among boxes;
  boxes at other credentials, with a stake part, or with hashed/malformed datums.
- **Mix:** zero, one, two, three, four and more boxes; too few or too many proofs;
  swapped proofs; wrong challenge length in each branch; inputs before, between and after
  boxes; missing or extra outputs; reordered outputs; extra box output after the prefix;
  changed output credential, stake credential, reference script or datum shape; changed
  lovelace, token policy, token name or token quantity; extra assets; ADA and token pools.
- **Reference NFT:** absent reference input; NFT under another policy or name; wrong
  quantity; more than one candidate; NFT before and after unrelated reference inputs;
  missing, hashed, malformed or altered reference datum; lookalike reference script and
  address; reference input also used as a normal input where the ledger permits it.
- **Fee shard:** missing or extra shards; fee output missing, duplicated or moved; changed
  fee datum, value or address; fee just below, equal to, and above the cap; owner redeemer,
  absent or different script redeemer, or key withdrawal; fewer than three boxes; fake
  box credentials; replenishment equal to, below, and above the previous balance.
- **Launch and composition:** seed absent, only referenced, spent once, or spent with other
  inputs; missing, extra or wrong-name NFTs; NFT sent to the wrong address or under a
  hashed/malformed datum; mix_box and mix_logic checked together with the actual ledger
  withdrawal rules; fee shard and mix_logic checked together; multiple pools in one
  transaction; duplicate or reordered map entries only where the ledger encoding allows
  them. Separate malformed-context tests from ledger-valid transaction claims.

The broader one-box Mix statement with an arbitrary proof was falsified when it required
`isUnsuccessful` (an error state) within 5,000 steps. The solver gave a long proof in a
malformed context. `LogicControls` reconstructs that proof: the evaluator is still running
at 5,000 steps and errors by 20,000. This illustrates the step bound for that instance; it
does not prove that all arbitrary proof payloads are rejected.
